## Rolling Notes & Discoveries

### Discovery 1 — The AP-2 Breakthrough

**What**: Replacing a dynamically-recursive Karatsuba with a statically-generated, fully-unrolled fixed-tree kernel (the "AP-2" specialization) eliminates ABI and stack pressure that the compiler cannot optimize away in a general recursive formulation.

**Why it matters**: RISC-V calling convention requires the compiler to save/restore callee-saved registers at every non-leaf frame. For deep Karatsuba trees (depth 8–10 for HQC-256), the aggregate spill/restore overhead dwarfs the actual arithmetic. By emitting one flat function per size via the code generator (`scripts/gen/gen_karatsuba_specialized.py`), the compiler sees a single large function body and can allocate registers globally, inline the leaf operations, and schedule loads/stores freely.

**Measured impact at HQC-128 vect_mul (instret)**:
| Implementation | instret |
|---|---|
| ref_scalar (schoolbook) | 19,213,918 |
| karatsuba_zbc (dynamic recursion) | ~600k (pre-AP2) |
| karatsuba_zbc (AP-2 fixed-tree) | **211,841** |
| karatsuba_rvv (AP-2, RVV leaves) | **157,377** |

**Key lesson**: For deeply-nested divide-and-conquer algorithms on register-starved ISAs, static code generation often beats a smart compiler by an order of magnitude because the compiler's ABI obligations are structural.

**Reference**: `src/poly_mul/scalar/karatsuba_zbc/karatsuba_specialized_gen.h` (generated by `scripts/gen/gen_karatsuba_specialized.py --mode zbc`).

### Discovery 2 — The Base RVV Keccak Paradox

**What**: Adding RVV vector instructions to the Keccak-f[1600] permutation *increased* the total instruction count compared to scalar Keccak with auto-vectorization.

**Why it happens**: Keccak-f requires an irregular 5×5-lane permutation (θ, ρ, π, χ, ι rounds). Each step needs:
- `vror.vv` (vector rotate) — **not available in base RVV 1.0**. Instead, implemented as `vsrl.vv + vsll.vv + vor.vv` (3 instructions instead of 1).
- `vrgather.vv` for the π step — a lane-gather with a compile-time constant permutation, but on base RVV `vrgather` carries significant microarchitecture overhead.
- The vector register file (32 × VLEN bits) adds pressure compared to 64-bit scalar GPRs for this 1600-bit-state computation.

**Measured decaps instret (HQC-128)**:
| Keccak implementation | decaps instret |
|---|---|
| `fips202_rvv_only.c` (hand-written RVV) | ~1.37M |
| `fips202.c` (scalar, auto-vectorized) | ~1.19M |

**The hybrid solution**: The Tier 2 (Edge) champion uses RVV for polynomial multiplication and Reed-Muller decoding (both benefit from data-parallel patterns with natural lane alignment), but reverts to scalar Keccak. The Keccak auto-mapping in `scripts/bench/lib_bench.sh` enforces this automatically for `karatsuba_rvv` and any `*_rvv` variant.

**Anticipated resolution**: The Zvbb extension adds `vror.vv` and `vandn.vv`, which should eliminate the 3-for-1 rotation penalty. Keccak on Zvbb targets is expected to outperform scalar. This is tracked as a future experiment (see `experiments/EXP-fafft-zvbc-towerfield/`).

**Hardware corollary (BPI-F3, 2026-05-31)**: On real hardware (SpacemiT K1 X60, GCC native), the auto-vectorization that Discovery 2 measures in Spike also manifests as a ~12% cycle reduction (359k → 314k cycles for HQC-128 Keccak). Crucially, `vector_ref` and `vector_rvv` produce *identical* Keccak results (~313.9k vs ~313.5k = noise) because the keccak binary (`bench_hw_keccak_hqc128`) compiles the same `fips202.c` source — only the `-march` and `-ftree-vectorize` flags differ, and both vector variants enable auto-vectorization. This is a correct and expected result: the keccak micro-bench measures "keccak cost under this variant's compilation environment," not "different keccak implementations." The ~12% benefit comes from GCC auto-vectorizing the θ/χ steps (XOR-parallel, no cross-lane deps) while leaving the ρ step scalar (irregular rotations without `vror.vv`). See `docs/thesis-helper/optimizations/miscellaneous.md` §7 for full analysis.

**Key lesson**: ISA completeness matters more than ISA width for irregular permutations. Profile at the micro-operation level before committing to a vector Keccak implementation.

### Discovery 3 — The 3-Tier Hardware Profile

**What**: HQC-RISC-V optimizations naturally stratify into three hardware deployment tiers with distinct ISA requirements and champion strategies.

**The tiers**:

| Tier | Target | ISA | Champion | vect_mul speedup (HQC-128) | decaps speedup (HQC-128) |
|------|--------|-----|----------|----------------------------|--------------------------|
| **1 — IoT** | Embedded, no V-ext | rv64gc + Zbc/Zbb/Zbkb | `karatsuba_zbc` AP-2 | x91 | x28 |
| **2 — Edge** | Application core + RVV | rv64gcv + Zbc/Zbb/Zbkb | `karatsuba_rvv` AP-2 (hybrid) | x118 | x41 |
| **3 — High-End** | Full crypto vector | rv64gcv + Zvbc/Zvbb/Zvl256b | `karatsuba_zvbc` AP-2 | x255 | x63 |

**Key architectural insights per tier**:

- **Tier 1**: The Zbc `clmul`/`clmulh` pair provides 64-bit GF(2)[x] multiply-accumulate in a single instruction. Karatsuba with static tree generation reduces the HQC-128 polynomial multiply from 19M to 211k instret (x91). The scalar ISA constraint is enforced via `-mno-vector` / `-mno-zvector` compile flags — this prevents the auto-vectorizer from emitting RVV instructions that would crash on Tier 1 hardware.

- **Tier 2**: Adding base RVV (V 1.0) unlocks vector carryless multiply (`vclmul.vv` from Zvbc is absent here), but the 64-bit scalar `clmul` with RVV recomposition loops outperforms pure-scalar Karatsuba. The hybrid Keccak architecture (scalar SHAKE) avoids the base-RVV rotation penalty and produces better end-to-end numbers than a naive "vectorize everything" approach.

- **Tier 3**: Zvbc's `vclmul.vv` operates on 64 parallel 64-bit elements per register group, enabling a fully-vectorized leaf kernel. The `vclmul_leaf` function replaces scalar `clmul` chains with a single vector instruction sequence, yielding x255 polymul speedup. The `zvl256b` constraint (minimum 256-bit vector length) is required for the inner 4-element tile to remain in a single register.

**Thesis narrative hook**: The tiered decomposition maps directly to RISC-V's modular ISA philosophy — each extension is optional, each variant is strictly controlled, and speedup scales predictably with extension adoption. This makes HQC an effective case study for evaluating the real-world payoff of post-quantum crypto extensions in the RISC-V roadmap.

**Reference**: `docs/thesis/METRICS_AGGREGATION.md`, generated tables via `python3 scripts/report/generate_speedups.py`.

### Discovery 4 — The Compiler Ceiling on Zvbb/Zvbc Flags

**Experiment**: A temporary baseline `ref_full_crypto` was compiled from the exact same unoptimized reference C sources (`gf2x.c`, `fips202.c`, scalar RM/RS) with
`-march=rv64gcv_zbc_zbb_zbkb_zvbb_zvbc` and auto-vectorization enabled.

**Result (HQC-128)**:
- `ref_vector` (`-march=rv64gcv_zbc_zbb_zbkb`):
	- `vect_mul`: 18,527,412 instret
	- `decaps`: 56,442,467 instret
- `ref_full_crypto` (`+zvbb+zvbc`):
	- `vect_mul`: 18,527,412 instret
	- `decaps`: 56,442,898 instret

The difference is statistically and practically negligible for deterministic Spike instret accounting (exactly identical for `vect_mul`; <0.001% drift for `decaps`).

**Conclusion**: Compilers do not automatically synthesize Zvbc/Zvbb crypto-vector primitives from generic C in this workload. Therefore `ref_vector` is the practical compiler ceiling baseline, and explicit hand-written intrinsic kernels remain necessary to realize Tier 3 gains.

### Discovery 5 — The Zbb Keccak Speedup

Before retiring the strict no-extension baseline (`ref_pure`), we measured
`KeccakF1600_StatePermute` at **918,882** instructions. Rebuilding the same
reference path with Zbb enabled (`ref_scalar`) reduced this to **578,792**.

This is a **37% reduction** from pure hardware support: native scalar rotate
(`rori`) eliminates synthesized rotate idioms that otherwise expand into
multiple shift/or instructions.

The key thesis interpretation is that this win is architectural rather than
algorithmic. No Keccak source rewrite was required; the improvement came from
ISA capability exposure.

---

### Discovery 6 — Amdahl's Law and the Polymul Ceiling

In isolation, `vect_mul` reaches roughly **90x** speedup (ref scalar path to
`karatsuba_zbc`). End-to-end `decaps`, however, is capped near **28x**.

This is a direct Amdahl's Law result: polynomial multiplication was originally
about 96% of `decaps`. Once that region is aggressively optimized, the
remaining ~4% (Keccak hashing plus scalar decode/control work) dominates the
new runtime. The whole-system speedup therefore asymptotically approaches the
25x-28x range even as `vect_mul` continues to improve.

For the thesis narrative, this is the central systems lesson: local kernel
speedups do not translate linearly to application-level speedups once bottleneck
ownership shifts.

### Discovery 7 — Why Larger VLEN Can Increase instret

**Observation**: In VLEN sweeps, increasing runtime VLEN (e.g., 256 → 512 → 1024)
does not guarantee lower instruction-retired counts for end-to-end KEM. In some
cases, instret rises.

**Interpretation**: This is not a Spike measurement bug by itself. It indicates
that the current code path does not scale instruction efficiency with wider vector
registers for those kernels.

**Why this can happen in practice**:

- **Fixed-width coding patterns**: Some RVV kernels are written around fixed
	chunk sizes and constants tuned for VLEN=256. If loops, pack/unpack steps,
	or lane management are not restructured for larger `vl`, wider vectors can
	introduce extra setup/shuffle work without proportional amortization.

- **VL-dependent control overhead**: `vsetvl`/boundary handling can change with
	VLEN and LMUL choices. If tail paths or loop trip geometry become less aligned,
	total dynamic instructions may increase.

- **Whole-KEM composition effects**: End-to-end KEM includes keypair/encaps/decaps,
	not only polymul. Even if polymul benefits slightly, non-scaling components
	(hashing, decode glue, control code) can dominate and flatten or invert the
	total-instret trend.

- **Configuration-path sensitivity**: The RVV decoder path is currently unstable
	for larger VLEN in this workflow, so VLEN sweeps pin decode to scalar `ref`
	for stable polymul-centric comparison. This is a methodological choice to avoid
	conflating decoder issues with polymul scaling.

**Thesis takeaway**: "Bigger VLEN" is not automatically "fewer instructions".
To realize gains, kernels must be explicitly VLEN-aware (loop structure,
tiling, LMUL/SEW strategy, and data layout), and full-pipeline effects must be
measured rather than inferred from a single hot function.

**Concrete examples from this repo's workflow**:

- `ref_vector` can show increasing KEM instret as VLEN grows (e.g., L128 run
	often trends upward from VLEN=256 to 2048). This indicates that wider runtime
	vector width does not map to fewer dynamic instructions for the current full
	KEM path.

- `karatsuba_rvv` with RVV decoder (`decode=rvv`) can hang for larger VLEN in
	the full-KEM sweep path. For stable VLEN polymul scaling comparison, the sweep
	pins `decode=ref` to isolate polymul effects from decoder instability.

**How to make kernels more VLEN-agnostic (and when it helps)**:

- **Strip-mined RVV loops everywhere**:
	- Use `for (; n > 0; n -= vl) { vl = vsetvl(...); ... }` patterns.
	- Avoid compile-time assumptions like "exactly 256-bit vectors" for loop body
		shape and tail handling.

- **Parameterize LMUL/SEW and tile geometry**:
	- Keep data movement and arithmetic tiles derived from `vl` instead of fixed
		constants tied to VLEN=256.
	- Benchmark candidate `(SEW, LMUL)` points and keep per-kernel defaults.

- **Reduce VLEN-sensitive overhead**:
	- Minimize repeated `vsetvl` inside inner loops.
	- Hoist invariant permutation/index vectors.
	- Prefer contiguous vector loads/stores over gather/scatter where possible.

- **Use multiversion + dispatcher when needed**:
	- A single generic kernel is possible, but highest performance often needs
		specialized paths (e.g., VLEN 256/512/1024 tuned variants) plus runtime
		dispatch.

**Practical conclusion**: VLEN-agnostic correctness is achievable; VLEN-agnostic
peak performance usually requires either autotuning or multi-versioned kernels.

### 5.3.1 Πίνακας Επιδόσεων HQC-128 ανά Αρχιτεκτονική

οποίος περιλαμβάνει αντιπροσωπευτικές υλοποιήσεις από ετερογενείς αρχιτεκτονικές.
Για τις μετρήσεις τρίτων χρησιμοποιούνται **κύκλοι ρολογιού** (clock cycles), ενώ
για την παρούσα RISC-V υλοποίηση αναφέρεται ο **αριθμός δυναμικά εκτελεσθεισών
εντολών** (`instret`), όπως καταγράφεται από τον ντετερμινιστικό προσομοιωτή Spike
ISS. Η αξιολόγηση καλύπτει το πλήρες KEM-τρίπτυχο: παραγωγή κλειδιών (KeyGen),
ενθυλάκωση (Encaps) και αποθυλάκωση (Decaps).

| **Παρούσα εργασία** (RV64GBV — `karatsuba_zvbc`) | instret | **155,539** | **335,585** | **679,740** | AP-2 fixed-tree, Zvbc + Zvbb, Spike ISS |

### 5.3.2 Αναλυτική Μικροαρχιτεκτονική Αξιολόγηση

#### Α. Το Χάσμα Υλικού Carry-less Πολλαπλασιασμού

Η αρχιτεκτονική ARM Cortex-M4 δεν διαθέτει νατιβή εντολή carry-less
πολλαπλασιασμού στο επίπεδο του ALU. Ως αποτέλεσμα, κάθε πολλαπλασιασμός
πολυωνύμων στο $\mathrm{GF}(2)[x]$ — ο οποίος αποτελεί τον υπολογιστικό πυρήνα
της κρυπτογραφικής λειτουργίας του HQC — υλοποιείται μέσω τεχνικών bit-slicing
ή μέσω πινάκων αναζήτησης (look-up tables) τύπου NTL. Οι προσεγγίσεις αυτές
μεταφράζουν κάθε λογικό βήμα πολλαπλασιασμού σε δεκάδες scalar εντολές,
εκθέτοντας εντατική ανταλλαγή (spill) καταχωρητών και υψηλό αριθμό προσβάσεων
στη μνήμη cache L1.

Ειδικότερα, η επιδόση Decaps στη Cortex-M4 φτάνει τους **7,502,580 κύκλους**,
έναντι **679,740 instret** της παρούσας RV64GBV υλοποίησης. Μολονότι η άμεση
σύγκριση μεταξύ κύκλων και instret είναι ετερογενής (βλ. §5.3.2.Γ), το απόλυτο
χάσμα υποδηλώνει πρόσθετο υπολογιστικό φόρτο της τάξης του **~1.000%**,
αντικατοπτρίζοντας άμεσα το κόστος απουσίας εξειδικευμένης υλικοτεχνικής
υποστήριξης για αλγεβρικές πράξεις στο $\mathrm{GF}(2)[x]$. Η παρατήρηση αυτή
ενισχύει τη θέση ότι η ενσωμάτωση επεκτάσεων τύπου Zbc/Zvbc στη RISC-V ISA δεν
αποτελεί αισθητική επιλογή σχεδιασμού, αλλά **αρχιτεκτονική αναγκαιότητα** για
αποδοτική μετα-κβαντική κρυπτογραφία σε ενσωματωμένα συστήματα.

#### Β. Το Παράδοξο των Καθαρά-Λογισμικών FAFFT Υλοποιήσεων

Ο αλγόριθμος Frobenius Additive Fast Fourier Transform (FAFFT), ο οποίος
θεμελιώνεται στις εργασίες των Gao–Mateer και Lin–Chung–Han, παρουσιάζει
**ασυμπτωτική πολυπλοκότητα $O(n \log n)$** για τον πολλαπλασιασμό πολυωνύμων
στο $\mathrm{GF}(2)[x]$, τοποθετώντας τον θεωρητικά πάνω από τους αλγορίθμους
Toom-Cook και Karatsuba, με πολυπλοκότητες $O(n^{\log_3 5})$ και
$O(n^{\log_2 3})$ αντίστοιχα. Παρ' όλα αυτά, σε καθαρά λογισμικές υλοποιήσεις
σε σκαλαριστούς RISC-V πυρήνες, ο FAFFT επιδεικνύει **38,099,269 κύκλους** για
Decaps HQC-128 — δηλαδή πλέον των **56× περισσότερους κύκλους** σε σχέση με την
παρούσα Karatsuba AP-2 υλοποίηση.

Η ρίζα της παραδοξότητας αυτής βρίσκεται στη μικροαρχιτεκτονική πραγματικότητα
των πράξεων FFT σε μη-εξειδικευμένο υλικό:

1. **Εντατική αναδιάταξη δεδομένων (data shuffling):** Κάθε στάδιο butterfly
   του FAFFT απαιτεί αναδιάταξη λωρίδων δεδομένων (lane permutations) που δεν
   αντιστοιχούν σε φυσικά cache-aligned μπλοκ. Σε απουσία διανυσματικών εντολών
   τύπου `vrgather.vv` του RVV, κάθε ανακατανομή επιβαρύνεται με πολλαπλές
   εντολές φόρτωσης/αποθήκευσης (load/store), αυξάνοντας δραματικά τον αριθμό
   δυναμικών εντολών.

2. **Κυριαρχία σταθερού όρου για πρακτικά μεγέθη:** Για μεγέθη πολυωνύμων τύπου
   HQC-128 ($n \approx 17{,}000$ bits), η ασυμπτωτική ανωτερότητα του
   $O(n \log n)$ δεν εκδηλώνεται σε πρακτικά μεγέθη χωρίς υλικοτεχνική
   επιτάχυνση των inner loop primitives. Ο σταθερός πολλαπλασιαστικός παράγοντας
   ξεπερνά την πολυπλοκότητα ενός επίπεδου, στατικά παραγόμενου δέντρου
   Karatsuba (AP-2) για τα συγκεκριμένα μεγέθη.

3. **Αναγκαιότητα εξειδικευμένου υλικού:** Σε αρχιτεκτονικές με ευρείς
   καταχωρητές AVX-512 (512-bit ZMM) ή με Zvbc `vclmul.vv`, ο FAFFT αναμένεται
   να επωφεληθεί σημαντικά, καθώς οι permutation και butterfly πράξεις
   αντιστοιχίζονται αποδοτικά σε SIMD lanes. Η απουσία τέτοιων πόρων σε
   σκαλαριστούς πυρήνες καθιστά την ασυμπτωτική ανωτερότητα ουσιαστικά
   θεωρητική για πρακτικά μεγέθη παραμέτρων HQC.

Το εύρημα αυτό δικαιώνει την επιλογή της AP-2 Karatsuba υλοποίησης ως champion
για όλα τα επίπεδα Tier 1/2/3 απουσία πλήρους vector-carryless υποστήριξης
μέσω Zvbc.

#### Γ. Μεθοδολογική Διαφοροποίηση: Κύκλοι Ρολογιού έναντι Μετρητή Εντολών (instret)

Είναι κρίσιμο να επισημανθεί ότι τα δεδομένα της παρούσας εργασίας χρησιμοποιούν
τον μετρητή **`instret`** (instruction-retired counter) του προσομοιωτή Spike ISS,
ο οποίος αντιπροσωπεύει τον **αριθμό δυναμικά εκτελεσθεισών εντολών** υπό ιδανικές
συνθήκες pipeline: χωρίς stalls κύκλων αναμονής, χωρίς λανθάνοντα χρόνο μνήμης
(memory latency) και χωρίς πρακτικές επιδράσεις ιεραρχίας cache.

Αντίθετα, οι μετρήσεις αναφοράς (Intel AVX-512, AMD Zen 4, ARM Cortex-M4)
αποτελούν **πραγματικούς κύκλους ρολογιού** μετρημένους σε φυσικό υλικό, οι
οποίοι ενσωματώνουν παραλληλισμό επιπέδου εντολών (ILP/OoO execution), την
ιεραρχία cache με TLB misses, εξαρτήσεις δεδομένων (data hazards) και θερμικές
επιδράσεις. Κατά συνέπεια, η **άμεση αριθμητική σύγκριση** μεταξύ instret και
κύκλων ρολογιού **δεν επιτρέπεται χωρίς επιφυλάξεις**.

Ωστόσο, ο instret αποτελεί **ισχυρό κάτω φράγμα κύκλων** σε κάθε ρεαλιστικό
pipeline: αν ένας αλγόριθμος απαιτεί λιγότερες δυναμικές εντολές, δεν μπορεί να
εκτελεστεί σε λιγότερους κύκλους παρά μόνο μέσω υπερβαθμωτής εκτέλεσης
(superscalar out-of-order) ή εξειδικευμένων execution units. Η θεμελιώδης
αρχιτεκτονική παρατήρηση της παρούσας εργασίας — ότι η βελτιστοποιημένη RISC-V
υλοποίηση με Zvbc/Zvbb επιτυγχάνει instret της **ίδιας τάξης μεγέθους** με τον
AVX-512 champion (~2–4× διαφορά στο Decaps), εκτελώντας ταυτόχρονα **~11×
λιγότερες εντολές** από τον βελτιστοποιημένο Cortex-M4 champion — αναδεικνύει
άπαξ και αμετάκλητα την αξία των στοχευμένων κρυπτογραφικών επεκτάσεων στο
RISC-V ISA. Η γεφύρωση του εναπομένοντος χάσματος έναντι AVX-512 αναμένεται
μέσω batching πολλαπλών KEM sessions και εκτέλεσης σε φυσικό RISC-V hardware με
νατιβή Zvbc υποστήριξη.

### Discovery 8 — GCC 15.x Zvbb Incompatibility (Investigated & Documented)

**What**: The `fips202_zvbb_x2.c` Keccak backend cannot be compiled by GCC. Two distinct issues were identified:

1. **Array-of-vector-type limitation (compile-time):** The x2 SoA path declares `vu64m1_fixed_t state[25]` — arrays of fixed-length RVV vector types via `__attribute__((riscv_rvv_vector_bits(N)))`. GCC rejects this because it treats all RVV types as *sizeless* (scalable) per the RVV spec. This attribute is a Clang-only language extension.

2. **LMUL=8 vrgather/vror codegen bug (runtime):** Even after implementing a GCC-compatible x2 path (using `uint64_t[50]` flat buffer with named `vuint64m1_t` locals), the single-stream `KeccakF1600_StatePermute` function — which uses LMUL=8 `vrgather.vv` + `vror.vv` (Zvbb) — produces code that runs forever on Spike. GCC 15.2 emits only 4 `vrgather` instructions (vs Clang's 52) and 1 `vror.vv` (vs Clang's 42), indicating severely broken codegen for this pattern.

**Investigation performed (2026-05-26):**
- Implemented a dual-path `#if defined(__clang__)` / `#elif defined(__GNUC__)` architecture
- GCC x2 path: `uint64_t[50]` flat buffer, 25 named `vuint64m1_t` locals, load-once/store-once around the 24-round loop
- GCC single-stream: linked vendor scalar `fips202.c` (since the Zvbb LMUL=8 path is broken)
- **Correctness verified:** KAT outputs bit-for-bit identical between Clang and GCC (100/100 vectors)
- **Performance measured:**

| Level | Clang (Zvbb) | GCC (scalar fallback) | GCC overhead |
|-------|-------------|----------------------|--------------|

Keccak micro-bench: Clang Zvbb = 2,033 instret, GCC scalar = 5,694 instret (+180%)

**Decision:** The ~80-90% overhead from the scalar Keccak fallback makes the GCC path not useful for performance comparison. The pre-build skip guard in `run_compiler_mode()` is retained:
```bash
if [[ "$compiler" == "gcc" && "$KECCAK_IMPL" == "zvbb_x2_soa" ]]; then
    echo "SKIP (gcc_zvbb_incompatible)"
    # ... write SKIP row to CSV
    continue
fi
```

**Root cause classification:**
- Issue 1 (array-of-vector): **Language extension gap** — GCC follows the RVV spec strictly (sizeless types), Clang extends it with `riscv_rvv_vector_bits`. No GCC fix expected without spec change.
- Issue 2 (LMUL=8 codegen): **GCC compiler bug** — the generated code enters an infinite loop. Likely a register allocation or instruction scheduling issue with LMUL=8 register groups (4 groups × 8 registers = all 32 vector registers consumed, leaving no room for temporaries without spilling, and the spill/reload logic appears broken).

**Thesis relevance (§8.4 Compiler Comparison):** Document as a known GCC limitation. The Zvbb Keccak backend is Clang-only. For GCC compiler comparison benchmarks, use `HQC_KECCAK_IMPL=ref` (vendor scalar) which works correctly on both compilers.

**Key lesson:** RISC-V vector crypto extensions (Zvbb/Zvbc) are still maturing in GCC's backend. For production crypto code targeting these extensions, Clang/LLVM is currently the only viable compiler. This is consistent with the broader RISC-V ecosystem where LLVM leads GCC in RVV extension support.
