\section{Σύγκριση με Ετερογενείς Αρχιτεκτονικές}
\label{sec:cross-architecture}

Η αξιολόγηση μιας κρυπτογραφικής υλοποίησης αποκτά πλήρες νόημα μόνο σε
σύγκριση με τις βέλτιστες υλοποιήσεις σε εναλλακτικές αρχιτεκτονικές.
Η ενότητα αυτή τοποθετεί τα αποτελέσματα της παρούσας εργασίας στο ευρύτερο
τοπίο υλοποιήσεων \HQC, αναλύοντας τόσο τα ποσοτικά δεδομένα όσο και τους
μεθοδολογικούς περιορισμούς μιας εγγενώς ετερογενούς σύγκρισης.

ανωτερότητα $\BigO{n \log n}$ δεν εκδηλώνεται χωρίς κατάλληλη hardware
υποστήριξη.

%% --------------------------------------------------------------------------
\subsection{Μεθοδολογική Επιφύλαξη: \instret έναντι Κύκλων Ρολογιού}
\label{ssec:methodology-caveat}

Η άμεση αριθμητική σύγκριση μεταξύ \instret και κύκλων ρολογιού δεν
επιτρέπεται χωρίς ρητές επιφυλάξεις.  Οι μετρήσεις αναφοράς ενσωματώνουν
παραλληλισμό επιπέδου εντολών (ILP), out-of-order εκτέλεση, ιεραρχία cache
και branch prediction — παράγοντες που ο Spike ISS δεν μοντελοποιεί.
Αντίστροφα, ο \instret αποτελεί \defterm{κάτω φράγμα κύκλων} σε κάθε
ρεαλιστικό pipeline: ένας αλγόριθμος δεν μπορεί να εκτελεστεί σε λιγότερους
κύκλους από τις δυναμικές εντολές του, εκτός εάν ο επεξεργαστής εκμεταλλεύεται
υπερβαθμωτή εκτέλεση (superscalar issue width $> 1$).

Η εκτίμηση CPI (Cycles Per Instruction) μέσω ανάλυσης instruction mix
(\cref{tab:cpi-estimate}) παρέχει μια ενδεικτική γέφυρα μεταξύ \instret και
αναμενόμενων κύκλων.  Για το Tier~3, η εκτιμώμενη CPI ανέρχεται σε $1.69$
(λόγω υψηλού ποσοστού vector memory operations, \pct{32.7} loads), οδηγώντας
σε εκτιμώμενους $\num{394225} \times 1.69 \approx \num{666238}$ κύκλους για
\Decaps — τιμή που παραμένει $\num{666238} / \num{300661} = 2.2\times$
υψηλότερη από τον AVX-512 champion.

Η αύξηση CPI από Tier~1 ($1.37$) σε Tier~3 ($1.69$) αντικατοπτρίζει τη
μετατόπιση του bottleneck: στο Tier~3, οι vector memory operations
(\insn{vle64.v}/\insn{vse64.v}) και οι vector crypto operations
(\vclmul/\vclmulh) κυριαρχούν στο instruction mix, εισάγοντας υψηλότερη
μέση latency ανά εντολή.  Παρ' όλα αυτά, η δραματική μείωση \instret
($\num{3449795} \to \num{716983}$, $-\pct{79}$) υπερκαλύπτει πλήρως την
αύξηση CPI ($+\pct{23}$), οδηγώντας σε καθαρή μείωση εκτιμώμενων κύκλων
κατά $\pct{74}$ μεταξύ Tier~1 και Tier~3.

Η μεθοδολογική θέση της παρούσας εργασίας ακολουθεί τη δομή αποδεικτικής
αλυσίδας που προτείνουν οι Zhang et al.\ \cite{zhang-tches2025}: (α)~πίνακας
\instret, (β)~εκτίμηση CPI μέσω instruction mix, (γ)~θεωρητική πρόβλεψη
IPC.  Η προσέγγιση αυτή αποτελεί αποδεκτή πρακτική στην κοινότητα \gls{pqc}
benchmarking \cite{pqm4, zhang-tches2025} για υλοποιήσεις που δεν διαθέτουν
πρόσβαση σε φυσικό hardware με τις απαιτούμενες extensions.

%% --------------------------------------------------------------------------
\subsection{Ανάλυση Χάσματος Cortex-M4: Η Αρχιτεκτονική Αναγκαιότητα
  του Carry-less Multiply}
\label{ssec:cortex-m4-gap}

Η αρχιτεκτονική ARM Cortex-M4 δεν διαθέτει εντολή carry-less
πολλαπλασιασμού στο επίπεδο ALU.  Κάθε πολλαπλασιασμός πολυωνύμων στο
$\GFpoly$ υλοποιείται μέσω bit-slicing ή πινάκων αναζήτησης (NTL
look-up tables), μεταφράζοντας κάθε λογικό βήμα σε δεκάδες scalar εντολές
με εντατική χρήση καταχωρητών και πολλαπλές προσβάσεις στη μνήμη L1
\cite{Jang2026-CortexM4-HQC}.

Η ποσοτική διαφορά είναι εντυπωσιακή: η \Decaps στον Cortex-M4 απαιτεί
\cycles{7502580} κύκλους, ενώ το Tier~3 της παρούσας εργασίας εκτελεί
\cycles{394225} δυναμικές εντολές — λόγος $19\times$.  Ακόμη και υπό τη
συντηρητική υπόθεση CPI $= 2.0$ για τον RISC-V pipeline (σημαντικά
υψηλότερη από την εκτιμώμενη $1.69$), οι αναμενόμενοι κύκλοι
($\approx\num{788450}$) παραμένουν $9.5\times$ χαμηλότεροι.

Η παρατήρηση αυτή δεν αποτελεί κριτική της αρχιτεκτονικής Cortex-M4 —
αντικατοπτρίζει τη θεμελιώδη αρχιτεκτονική αναγκαιότητα εξειδικευμένων
εντολών για αποδοτική μετα-κβαντική κρυπτογραφία βασισμένη σε κώδικες.
Η ενσωμάτωση \Zbc/\Zvbc στο RISC-V ISA δεν αποτελεί αισθητική σχεδιαστική
επιλογή αλλά προϋπόθεση ανταγωνιστικής απόδοσης σε code-based \gls{pqc}.

\subsection{Το Παράδοξο FAFFT: Ασυμπτωτική Ανωτερότητα χωρίς Πρακτική
  Εκδήλωση}
\label{ssec:fafft-paradox}

Ο αλγόριθμος Frobenius Additive FFT (FAFFT) παρουσιάζει ασυμπτωτική
πολυπλοκότητα $\BigO{n \log n}$ για τον πολυωνυμικό πολλαπλασιασμό στο
$\GFpoly$, θεωρητικά ανώτερη από τον Karatsuba ($\BigO{n^{\log_2 3}}
\approx \BigO{n^{1.585}}$).  Παρ' όλα αυτά, η pure-software FAFFT
υλοποίηση σε scalar RISC-V (CV32E40P) \cite{ras-nist2025} απαιτεί
\cycles{38099269} κύκλους για \Decaps HQC-128 — $96.6\times$ περισσότερους
από τους \cycles{394225} \instret του Tier~3 Karatsuba.

Τρεις δομικοί παράγοντες εξηγούν αυτό το παράδοξο.

\paragraph{Εντατική αναδιάταξη δεδομένων.}
Κάθε στάδιο butterfly του FAFFT απαιτεί αναδιάταξη λωρίδων δεδομένων (lane
permutations) που δεν αντιστοιχούν σε φυσικά cache-aligned μπλοκ.  Σε
απουσία vector permutation εντολών (\insn{vrgather.vv}), κάθε ανακατανομή
επιβαρύνεται με πολλαπλές εντολές load/store, αυξάνοντας δραματικά τον
αριθμό δυναμικών εντολών.

\paragraph{Κυριαρχία σταθερού όρου σε πρακτικά μεγέθη.}
Για μεγέθη πολυωνύμων τύπου HQC-128 ($N \approx \num{17000}$ bits), η
ασυμπτωτική ανωτερότητα $\BigO{n \log n}$ δεν εκδηλώνεται χωρίς
hardware επιτάχυνση των inner-loop primitives.  Ο σταθερός
πολλαπλασιαστικός παράγοντας (evaluation/interpolation overhead, tower-field
αριθμητική) υπερβαίνει τη μείωση sub-problems που παρέχει η FFT δομή.
Η πειραματική επιβεβαίωση μέσω πλήρους Toom-Cook~3 υλοποίησης
(βλ.\ \cref{sec:polymul-assessment}) κατέδειξε $4$–$5\times$ regression
αντί βελτίωσης.

\paragraph{Ασυμβατότητα tower-field με \vclmul.}
Ο FAFFT λειτουργεί σε extension fields $\GF{2^m}$ μέσω tower-field
αναπαράστασης.  Η εντολή \vclmul εκτελεί carry-less πολλαπλασιασμό σε
$\GF{2}[x]$ (πολυωνυμική αναπαράσταση) — δεν υποστηρίζει απευθείας
αριθμητική σε tower-field βάσεις.  Η μετατροπή μεταξύ αναπαραστάσεων
(change-of-basis) εισάγει πρόσθετο κόστος που εξουδετερώνει το
ασυμπτωτικό πλεονέκτημα \cite{Chen2026-TCHES-HQC-FFT}.

Η ανάλυση αυτή δικαιώνει την επιλογή Karatsuba AP-2 ως champion αλγορίθμου
σε όλα τα tiers.  Η FAFFT αποκτά πρακτική αξία μόνο σε αρχιτεκτονικές με
ευρείς SIMD registers (AVX-512 ZMM) ή με εξειδικευμένο hardware accelerator
(ANDROMEDA \cite{Ras2026-FAFFT-RISCV}) — σενάρια εκτός του πεδίου εφαρμογής
της παρούσας pure-software υλοποίησης.

%% --------------------------------------------------------------------------
\subsection{Τοποθέτηση έναντι AVX-512: Ανάλυση Εναπομένοντος Χάσματος}
\label{ssec:avx512-gap}

Ο Intel AVX-512 champion αποτελεί τη βέλτιστη δημοσιευμένη υλοποίηση \HQC
σε οποιαδήποτε πλατφόρμα.  Η ανάλυση του εναπομένοντος χάσματος ($1.31\times$
σε \instret, $\approx 2.2\times$ σε εκτιμώμενους κύκλους) αποκαλύπτει τρεις
δομικούς παράγοντες.

\paragraph{Εύρος SIMD.}
Η εντολή \code{VPCLMULQDQ} επεξεργάζεται $4 \times 64$-bit carry-less
products ανά εντολή σε 512-bit ZMM registers.  Η αντίστοιχη \vclmul στο
\VLEN$= \num{256}$ επεξεργάζεται $4 \times 64$-bit products σε LMUL$=$m1 —
ισοδύναμο throughput ανά εντολή.  Η διαφορά δεν βρίσκεται στο carry-less
multiply αλλά στις βοηθητικές πράξεις: ο AVX-512 διαθέτει 32 ZMM registers
($\num{2048}$ bytes register file) έναντι 32 vector registers $\times$
\SI{256}{bits} ($= \SI{1024}{\byte}$) στο \VLEN$= \num{256}$.  Η μεγαλύτερη
register file μειώνει τα spills κατά τη Karatsuba interpolation.

\paragraph{Out-of-order εκτέλεση.}
Οι Intel desktop cores (Golden Cove, Zen~4) εκτελούν 5–6 micro-ops ανά
κύκλο μέσω out-of-order scheduling, εκμεταλλευόμενοι τον παραλληλισμό
μεταξύ ανεξάρτητων Karatsuba sub-problems.  Ο SpacemiT K1 X60 (dual-issue,
in-order) δεν μπορεί να αξιοποιήσει αυτόν τον παραλληλισμό — κάθε εντολή
εκτελείται σειριακά εκτός εάν ο compiler εκθέτει ρητά ILP μέσω instruction
scheduling.

\paragraph{Ωριμότητα οικοσυστήματος.}
Η υλοποίηση AVX-512 \HQC αξιοποιεί δεκαετίες βελτιστοποίησης compiler
backends (ICC, GCC, Clang) για x86 SIMD, ενώ η RISC-V vector crypto
υποστήριξη στον LLVM βρίσκεται ακόμη σε πρώιμο στάδιο
(βλ.\ \cref{sec:compiler-comparison}).

Παρά τους παράγοντες αυτούς, η σύγκλιση σε $1.31\times$ \instret
τεκμηριώνει ότι η αλγοριθμική αποδοτικότητα της RISC-V υλοποίησης είναι
ανταγωνιστική — το εναπομένον χάσμα αποδίδεται κυρίως σε
μικροαρχιτεκτονικούς παράγοντες (issue width, register file depth) παρά
σε αλγοριθμική υστέρηση.  Η γεφύρωση αναμένεται μέσω: (α)~εκτέλεσης σε
out-of-order RISC-V cores με ευρύτερο \VLEN (RVA23 profile targets), και
(β)~batching πολλαπλών \KEM sessions για αξιοποίηση pipeline parallelism.

\subsection{Σύνοψη Ετερογενούς Σύγκρισης}
\label{ssec:cross-arch-summary}

Η ετερογενής σύγκριση αποκαλύπτει τρία θεμελιώδη ευρήματα.  Πρώτον, η
παρουσία hardware carry-less multiply αποτελεί τον κυρίαρχο παράγοντα
απόδοσης σε code-based \gls{pqc} — η διαφορά μεταξύ αρχιτεκτονικών με
(\Zbc, \code{PCLMULQDQ}, \code{PMULL}) και χωρίς (Cortex-M4) τέτοια
υποστήριξη υπερβαίνει μία τάξη μεγέθους.  Δεύτερον, η ασυμπτωτική
πολυπλοκότητα αλγορίθμου (FAFFT $\BigO{n \log n}$ έναντι Karatsuba
$\BigO{n^{1.585}}$) δεν μεταφράζεται σε πρακτικό πλεονέκτημα χωρίς
κατάλληλη hardware υποστήριξη — η επιλογή αλγορίθμου πρέπει να
συν-σχεδιάζεται με την αρχιτεκτονική στόχο.  Τρίτον, η RISC-V υλοποίηση
με ratified extensions επιτυγχάνει αλγοριθμική αποδοτικότητα ανταγωνιστική
του AVX-512 champion ($1.31\times$ σε \instret), τεκμηριώνοντας ότι η
modular ISA φιλοσοφία του RISC-V παρέχει επαρκή εργαλεία για αποδοτική
\gls{pqc} χωρίς custom hardware.

\section{ISA Ablation Study}
\label{sec:isa-ablation}

Η ενότητα αυτή απομονώνει τη συνεισφορά κάθε \gls{isa} extension στην
τελική απόδοση, μέσω συστηματικών ablation πειραμάτων.  Κάθε extension
αφαιρείται μεμονωμένα από τη \code{-march} σημαία μεταγλώττισης και
μετράται η επίπτωση στο \instret μέσω ντετερμινιστικής εκτέλεσης στον
Spike \gls{iss}.  Η μεθοδολογία αυτή παρέχει αιτιώδη αντιστοίχιση μεταξύ
hardware δυνατοτήτων και αλγοριθμικής απόδοσης — πληροφορία κρίσιμη τόσο
για σχεδιαστές hardware (ποιες extensions αξίζει να υλοποιηθούν) όσο και
για προγραμματιστές (ποιες extensions πρέπει να στοχεύσουν).

\subsection{Zba Address-Generation — Αποτελέσματα Ablation}
\label{ssec:zba-ablation}

Η extension \ext{Zba} παρέχει εντολές address generation (\insn{sh1add},
\insn{sh2add}, \insn{sh3add}) που συγχωνεύουν ένα shift-left με πρόσθεση
σε μία μόνο εντολή.  Ο μηχανισμός βελτιστοποίησης περιγράφεται στο
\cref{ssec:zba-address-gen} — η παρούσα ενότητα παρουσιάζει τα ποσοτικά
αποτελέσματα.

Ο \cref{fig:zba-ablation} αποκαλύπτει έντονη ασυμμετρία μεταξύ variants.
Η \code{karatsuba\_zvbc} ωφελείται κατά $-\pct{5.61}$ στο polymul hotspot
και $-\pct{3.27}$ στο πλήρες \KEM, ενώ η \code{karatsuba\_zbc} παρουσιάζει
μηδενική βελτίωση ($-\pct{0.004}$).

  \centering
  \input{figures/ch9-discussion/zba-ablation-bar}
  \caption{Επίδραση \ext{Zba} στο polymul \instret ανά variant (HQC-128).
    Η βελτίωση συσχετίζεται με την πυκνότητα δυναμικών pointer-scaling

Η ερμηνεία της ασυμμετρίας βρίσκεται στη δομή του hot path.  Στην
\code{karatsuba\_zvbc}, οι vector leaf κλήσεις (\code{vclmul\_leaf})
λειτουργούν σε pointer-addressed array slices — κάθε αναδρομικό επίπεδο
υπολογίζει \code{a + half} για \code{uint64\_t*} δείκτες, εκπέμποντας
\code{slli reg, half, 3} + \code{add reg, base, reg}.  Με \ext{Zba}, αυτό
γίνεται μία εντολή \insn{sh3add}.  Ο Karatsuba tree για HQC-128 εκτελεί
$\approx 70$ αναδρομικές κλήσεις, καθεμία με 3–5 pointer υπολογισμούς —
συνολικά 210–350 ζεύγη \code{slli+add} που συγχωνεύονται.

Αντίθετα, στην \code{karatsuba\_zbc} ο scalar leaf (\code{clmul\_leaf\_n8})
είναι πλήρως ξεδιπλωμένος με σταθερές μετατοπίσεις: κάθε πρόσβαση
\code{r[7]} επιλύεται σε compile-time σε σταθερό offset από τον base
register.  Η \ext{Zba} δεν έχει τίποτα να συγχωνεύσει στο hot loop —
η εξοικονόμηση περιορίζεται στον εξωτερικό αναδρομικό κώδικα, ο οποίος
αποτελεί αμελητέο ποσοστό του συνολικού \instret.

Η \code{karatsuba\_rvv} παρουσιάζει ενδιάμεση βελτίωση ($-\pct{1.03}$
polymul, $-\pct{0.67}$ \KEM) διότι χρησιμοποιεί scalar \clmul leaves
(σταθερές μετατοπίσεις, μη ωφελούμενα) αλλά \RVV recomposition helpers
με strip-mining loops (\code{ptr += vl} → \insn{sh3add}), οι οποίοι
ωφελούνται μερικώς.

Η \ext{Zba} ενεργοποιήθηκε στα \code{-march} strings των Tier~2 και
Tier~3 variants.  Η extension ανήκει στο RVA22U64 profile — κάθε
standards-conformant application processor που υλοποιεί \RVV παρέχει
ήδη \ext{Zba}, επομένως η ενεργοποίηση δεν εισάγει πρόσθετη hardware
απαίτηση.

η συνάρτηση δεν βρίσκεται στο vector hot path.

(\code{rv64gc\_zbc\_zbb\_zbs}).  Η προσθήκη στα vector variant march
strings δεν δικαιολογείται λόγω μηδενικής επίδρασης.

\subsection{Compiler Auto-Lowering — Όρια και Ευρήματα}
\label{ssec:ablation-auto-lowering}

Η ανάλυση ablation αποκαλύπτει ένα θεμελιώδες όριο στη δυνατότητα του
compiler να αξιοποιεί αυτόματα τις διαθέσιμες extensions.  Ο
\cref{tab:auto-lowering} κατηγοριοποιεί τις extensions σε δύο ομάδες:
αυτές που εκπέμπονται αυτόματα μέσω pattern recognition (auto-lowering)
και αυτές που απαιτούν ρητή χρήση intrinsics.

\begin{table}[htbp]
  \centering
  \caption{Όριο auto-lowering: ο compiler (Clang~21, \code{-O3})
    αναγνωρίζει αυτόματα scalar idioms αλλά δεν συνθέτει vector crypto
    primitives από generic C.  Η στήλη \q{Auto} δηλώνει εάν η εντολή
    εκπέμπεται χωρίς ρητή παρέμβαση του προγραμματιστή.}
  \label{tab:auto-lowering}
  \small
  \input{figures/ch9-discussion/auto-lowering-boundary}
\end{table}

\paragraph{Scalar auto-lowering.}
Ο Clang αναγνωρίζει αξιόπιστα τα ακόλουθα C idioms και εκπέμπει τις
αντίστοιχες εντολές χωρίς manual intervention, αρκεί η extension να
είναι ενεργή στο \code{-march} flag:

\begin{itemize}
  \item \code{(x << n) | (x >> (64-n))} → \rori (\Zbb)
  \item \code{\textasciitilde a \& b} → \insn{andn} (\Zbb)
  \item \code{base + idx*8} → \insn{sh3add} (\ext{Zba})
  \item \code{x |= (1ULL << pos)} → \insn{bset} (\ext{Zbs})
\end{itemize}

Η αξιοπιστία αυτή επιβεβαιώθηκε πειραματικά: η μεταγλώττιση του vendor
Keccak (\code{fips202.c}) με \code{-march=rv64gc\_zbc\_zbb} παράγει
ακριβώς \num{58} εντολές \rori — ταυτόσημο αποτέλεσμα με τη ρητή χρήση
\code{\_\_builtin\_rotateleft64}.  Η διαφορά \instret μεταξύ auto-lowered
και explicit builtin ανέρχεται σε $-\num{546}$ εντολές ($-\pct{0.0005}$),
εντός θορύβου μέτρησης.

\paragraph{Vector crypto: αδυναμία αυτόματης σύνθεσης.}
Σε αντίθεση με τα scalar patterns, ο compiler δεν συνθέτει αυτόματα
\Zvbc/\Zvbb primitives από generic C.  Η πειραματική τεκμηρίωση
προέρχεται από δύο ανεξάρτητες παρατηρήσεις:

\begin{enumerate}
  \item \textbf{Ablation \code{ref\_full\_crypto}:} Η μεταγλώττιση του
    ίδιου unoptimized reference C (\code{gf2x.c}, \code{fips202.c}) με
    \code{-march=rv64gcv\_zbc\_zbb\_zvbb\_zvbc} και auto-vectorization
    ενεργή παράγει \emph{ταυτόσημο} \instret με τη μεταγλώττιση χωρίς
    \Zvbc/\Zvbb: \code{vect\_mul} = \cycles{18527412} σε αμφότερες τις
    περιπτώσεις.  Ο compiler δεν εκπέμπει ούτε μία εντολή \vclmul ή
    \insn{vror.vv} από generic C loops.

  \item \textbf{CI opcode verification:} Το script
    \code{check\_opcodes.sh} επαληθεύει σε κάθε push ότι τα vector
    variant ELFs περιέχουν \vclmul/\vclmulh — εντολές που εμφανίζονται
    \emph{αποκλειστικά} λόγω ρητών intrinsics στον πηγαίο κώδικα.
    Χωρίς τα hand-written intrinsic kernels, κανένα \vclmul δεν θα
    υπήρχε στο binary.
\end{enumerate}

Η αδυναμία αυτή δεν αποτελεί σφάλμα του compiler — αντικατοπτρίζει τη
σημασιολογική πολυπλοκότητα των vector crypto operations.  Η εντολή
\vclmul εκτελεί carry-less πολλαπλασιασμό (XOR αντί ADD στα partial
products) — μια σημασιολογία που δεν αντιστοιχεί σε κανένα standard C
operator.  Ο compiler δεν μπορεί να αναγνωρίσει ότι ένας generic
shift-and-XOR loop υλοποιεί carry-less multiplication, διότι η
αντιστοίχιση απαιτεί αλγοριθμική γνώση πέρα από pattern matching.

\paragraph{Αρχιτεκτονική συνέπεια.}
Η παρατήρηση αυτή τεκμηριώνει τη σχεδιαστική επιλογή των Κεφαλαίων~6–7:
τα scalar paths χρησιμοποιούν plain C με auto-lowering (ο compiler
αξιοποιεί αυτόματα \Zbb/\ext{Zba}/\ext{Zbs}), ενώ τα vector paths
απαιτούν ρητά intrinsics (\code{\_\_riscv\_vclmul\_vv\_u64m1()},
\code{\_\_riscv\_vror\_vv\_u64m1()}).  Η διαφοροποίηση δεν είναι
αυθαίρετη — αντικατοπτρίζει ένα θεμελιώδες όριο στη δυνατότητα
αυτόματης βελτιστοποίησης: ο compiler μπορεί να αναγνωρίσει
\emph{αριθμητικά} patterns (rotate, shift-add) αλλά όχι
\emph{αλγεβρικά} patterns (carry-less multiplication σε $\GFpoly$).

\paragraph{Zbb: υποχρεωτική extension χωρίς manual intervention.}
Η ανάλυση ablation στο Tier~1 champion (\code{karatsuba\_zbc}) αποκαλύπτει
ότι η αφαίρεση \Zbb εισάγει $+\pct{10.48}$ overhead στο HQC-128 \KEM
(βλ.\ \cref{tab:zbb-ablation-tier1}).  Η επιβάρυνση προέρχεται
αποκλειστικά από τον Keccak πυρήνα: κάθε μία από τις \num{58} rotations
ανά permutation call εκτείνεται από μία εντολή \rori σε τρεις εντολές
(\code{slli + srli + or}).  Η φθίνουσα τάση ($\pct{10.48}$ στο L128 →
$\pct{5.95}$ στο L256) επιβεβαιώνει φαινόμενο Amdahl: ο Karatsuba
πολυωνυμικός πολλαπλασιασμός κλιμακώνεται υπεργραμμικά με το security
level, ενώ ο αριθμός Keccak rotations παραμένει σταθερός.

διαθεσιμότητας: κάθε processor με \ext{Zbkb} υλοποιεί και \Zbb, αλλά
το αντίστροφο δεν ισχύει.

\section{Code Size vs Performance Trade-off}
\label{sec:code-size-tradeoff}

\section{Σχεδιαστικές Αρχές που Γενικεύονται}
\label{sec:general-principles}

Η βελτιστοποίηση του \HQC σε RISC-V ανέδειξε σχεδιαστικές αρχές που
υπερβαίνουν τον συγκεκριμένο αλγόριθμο.  Οι αρχές αυτές αφορούν κάθε
κρυπτογραφική υλοποίηση που στοχεύει πολυωνυμική αριθμητική σε δυαδικά
πεδία, vector-length-agnostic εκτέλεση, ή αξιοποίηση εξειδικευμένων ISA
extensions σε in-order pipelines.  Η ενότητα αυτή αποστάζει τέσσερις
θεμελιώδεις αρχές από την εμπειρία τριών tiers υλοποίησης.

%% --------------------------------------------------------------------------
\subsection{Αρχή 1: Η Αποδοτικότητα του Carry-less Multiply ως Θεμελιώδης
  Μοχλός}
\label{ssec:principle-clmul}

Η εντολή \clmul μετασχηματίζει τον πολυωνυμικό πολλαπλασιασμό στο $\GFpoly$
από αλγοριθμικό πρόβλημα σε πρόβλημα data movement.  Η αντικατάσταση του
bit-serial schoolbook ($64n$ conditional shift-XOR ανά ζεύγος words) με ένα
ζεύγος \clmul/\clmulh (δύο εντολές ανά ζεύγος) μειώνει τον αριθμό δυναμικών
εντολών κατά δύο τάξεις μεγέθους στο leaf level.  Η μετάβαση στο vector
αντίστοιχο (\vclmul/\vclmulh) εξαλείφει επιπλέον τον scalar loop overhead,
επεξεργάζοντας $\VLMAX$ products ανά εντολή.

Η αρχή γενικεύεται σε κάθε αλγόριθμο που βασίζεται σε πολυωνυμικό
πολλαπλασιασμό στο $\GFpoly$: BIKE (QC-MDPC decoding), AES-GCM (GHASH
authentication), CRC-32 (Ethernet/storage checksums), και binary BCH codes.
Σε κάθε περίπτωση, η παρουσία hardware carry-less multiply αποτελεί τον
κυρίαρχο παράγοντα απόδοσης — η αλγοριθμική πολυπλοκότητα ($\BigO{n^2}$
schoolbook, $\BigO{n^{1.585}}$ Karatsuba, $\BigO{n \log n}$ FFT) καθίσταται
δευτερεύουσα όταν η σταθερά ανά leaf operation μειώνεται κατά $64\times$.

Η πρακτική συνέπεια για σχεδιαστές hardware είναι σαφής: η ενσωμάτωση
\Zbc/\Zvbc σε ένα RISC-V core αποτελεί προϋπόθεση ανταγωνιστικής απόδοσης
σε code-based \gls{pqc}, ανεξαρτήτως αλγοριθμικής επιλογής.  Η ablation
ανάλυση (\cref{ssec:ablation-quantitative}) τεκμηρίωσε ότι η \Zbc μόνη
παρέχει $-\pct{96}$ μείωση \instret στο polymul — καμία αλγοριθμική
βελτιστοποίηση δεν μπορεί να αντισταθμίσει την απουσία αυτής της εντολής.

%% --------------------------------------------------------------------------
\subsection{Αρχή 2: Η Αξία του Vector-Length Agnosticism σε Κρυπτογραφικά
  Workloads}
\label{ssec:principle-vla}

Η φιλοσοφία \defterm{Vector-Length Agnosticism} (VLA) του RVV 1.0 — ο ίδιος
κώδικας εκτελείται σε οποιοδήποτε \VLEN χωρίς recompilation — αποδεικνύεται
ιδιαίτερα πολύτιμη σε κρυπτογραφικά workloads για τρεις λόγους.

\paragraph{Αυτόματη κλιμάκωση throughput.}
Ο strip-mining βρόχος (\code{vl = vsetvl(n); /* vector ops */; n -= vl})
εκμεταλλεύεται αυτόματα ευρύτερα vector registers χωρίς αλλαγή πηγαίου
κώδικα.  Στην παρούσα εργασία, η μετάβαση από $\VLEN = \num{256}$ σε
$\VLEN = \num{1024}$ (sweep στον Spike) μείωσε τον αριθμό loop iterations
κατά $4\times$ στα combine loops — χωρίς καμία τροποποίηση στον κώδικα.
Η ίδια binary θα αξιοποιήσει αυτόματα μελλοντικό hardware με $\VLEN =
\num{2048}$.

\paragraph{Αποφυγή VLEN-specific code paths.}
Σε αρχιτεκτονικές σταθερού εύρους SIMD (AVX-256, AVX-512, NEON), κάθε
αλλαγή εύρους απαιτεί ξεχωριστό code path ή runtime dispatch.  Η
υλοποίηση AVX-512 \HQC \cite{Chen2026-TCHES-HQC-FFT} δεν εκτελείται σε
AVX-256 hardware χωρίς fallback path.  Αντίθετα, η VLA υλοποίηση της
παρούσας εργασίας εκτελείται ορθά σε κάθε $\VLEN \geq 128$ — από
embedded cores ($\VLEN = \num{128}$) έως high-performance designs
($\VLEN = \num{2048}$).

\paragraph{Constant-time εγγυήσεις ανεξαρτήτως VLEN.}
Η VLA δομή εγγυάται ότι η ροή ελέγχου εξαρτάται αποκλειστικά από δημόσιες
παραμέτρους (μέγεθος πολυωνύμου, security level) και όχι από μυστικά
δεδομένα — ανεξαρτήτως του \VLEN που επιλέγει το hardware.  Ο αριθμός
iterations αλλάζει, αλλά η ακολουθία εντολών εντός κάθε iteration παραμένει
ντετερμινιστική.  Η ιδιότητα αυτή απλοποιεί σημαντικά τη constant-time
επαλήθευση (βλ.\ \cref{sec:ct-verification}).

Η αρχή αυτή γενικεύεται πέρα από τον \HQC: κάθε κρυπτογραφικός πυρήνας
που επεξεργάζεται arrays σταθερού μεγέθους (NTT coefficients, Keccak state
lanes, AES blocks) ωφελείται από VLA strip-mining.  Η εναλλακτική —
fixed-width SIMD intrinsics — εισάγει maintenance burden ανάλογο του
αριθμού υποστηριζόμενων πλατφορμών.

%% --------------------------------------------------------------------------
\subsection{Αρχή 3: Τα Όρια Auto-Vectorization σε Crypto Kernels}
\label{ssec:principle-auto-vec-limits}

Η ανάλυση ablation (\cref{ssec:ablation-auto-lowering}) τεκμηρίωσε ένα
θεμελιώδες όριο: ο compiler αναγνωρίζει αξιόπιστα \emph{αριθμητικά}
patterns (rotate → \rori, shift-add → \insn{sh3add}) αλλά αδυνατεί να
συνθέσει \emph{αλγεβρικά} primitives (carry-less multiplication, vector
rotations σε crypto context) από generic C.  Η παρατήρηση αυτή δεν
αποτελεί σφάλμα compiler — αντικατοπτρίζει θεμελιώδη σημασιολογική
ασυμμετρία.

Η πρακτική συνέπεια ορίζει ένα σαφές \defterm{όριο αυτοματοποίησης}
(automation boundary) στο φάσμα προγραμματισμού RISC-V
(βλ.\ \cref{sec:programming-methods}):

\begin{itemize}
  \item \textbf{Κάτω από το όριο} (scalar bit-manipulation): plain C αρκεί.
    Ο compiler εκπέμπει αυτόματα \rori, \insn{andn}, \insn{sh3add},
    \insn{bset} χωρίς manual intervention.  Η ρητή χρήση intrinsics δεν
    παρέχει πρόσθετο όφελος.
  \item \textbf{Πάνω από το όριο} (vector crypto operations): ρητά intrinsics
    είναι υποχρεωτικά.  Η εντολή \vclmul δεν εκπέμπεται ποτέ αυτόματα —
    ο compiler δεν μπορεί να αναγνωρίσει ότι ένας shift-and-XOR loop
    υλοποιεί carry-less multiplication.
\end{itemize}

Η αρχή γενικεύεται σε κάθε domain-specific ISA extension: οι εντολές AES
(\insn{vaesz.vs}, \insn{vaesem.vs}), SM4 (\insn{vsm4r.vs}), και SHA-256
(\insn{vsha2ms.vv}) αντιμετωπίζουν το ίδιο όριο — κανένας compiler δεν
θα συνθέσει αυτόματα ένα AES round από generic C XOR/shift operations.
Η σχεδιαστική συνέπεια είναι ότι κάθε κρυπτογραφική υλοποίηση που
στοχεύει domain-specific extensions πρέπει να αποδεχθεί τη χρήση
intrinsics ως αναπόφευκτη — η εναλλακτική (inline assembly) εισάγει
opacity στον compiler optimizer χωρίς πρόσθετο λειτουργικό όφελος.

Η παρατήρηση αυτή έχει σημαντικές επιπτώσεις στη φορητότητα: ο κώδικας
που χρησιμοποιεί \code{\_\_riscv\_vclmul\_vv\_u64m1()} δεν μεταφέρεται
σε ARM ή x86 χωρίς rewrite.  Η VLA δομή (Αρχή~2) μετριάζει αυτό το
πρόβλημα εντός του RISC-V οικοσυστήματος — ο κώδικας παραμένει φορητός
μεταξύ \emph{διαφορετικών RISC-V hardware} — αλλά η cross-ISA portability
απαιτεί abstraction layers ή conditional compilation.

%% --------------------------------------------------------------------------
\subsection{Αρχή 4: Metaprogramming έναντι Hand-Tuning — Η Αξία της
  Παραγωγής Κώδικα}
\label{ssec:principle-metaprogramming}

Η πλήρης εξειδίκευση του Karatsuba recursion tree (AP-2,
\cref{ssec:ap2-generator}) αποτελεί παράδειγμα \defterm{metaprogramming}:
ένα Python script (\code{gen\_karatsuba\_specialized.py}) διασχίζει τον
αναδρομικό δέντρο σε compile-time και εκπέμπει εξειδικευμένες C
συναρτήσεις με σταθερές buffer offsets, loop bounds, και child dispatch.
Η προσέγγιση αυτή συνδυάζει τα πλεονεκτήματα δύο αντίθετων στρατηγικών:

\paragraph{Πλεονεκτήματα έναντι χειροκίνητου unrolling.}
Ο code generator παράγει εξειδικευμένο κώδικα για τρία security levels
($N \in \{277, 561, 901\}$) και τέσσερα backends (\code{zbc}, \code{rvv},
\code{zvbc}, \code{deferred}) — συνολικά \num{12} configurations — από
μία μόνο πηγή αλήθειας.  Η χειροκίνητη συγγραφή \num{12} εξειδικευμένων
υλοποιήσεων θα εισήγαγε ασυνέπειες και maintenance burden.  Κάθε
αλγοριθμική βελτίωση (direct-write discipline, overlap-save strategy)
εφαρμόζεται μία φορά στον generator και διαδίδεται αυτόματα σε όλα τα
configurations.

\paragraph{Πλεονεκτήματα έναντι generic runtime code.}
Ο παραγόμενος κώδικας εξαλείφει κάθε runtime overhead: threshold
comparisons, dynamic pointer arithmetic, recursion stack frames.  Ο
compiler λαμβάνει integer literals αντί μεταβλητών, ενεργοποιώντας
constant propagation, dead-code elimination, και πλήρες loop unrolling
σε μικρά μεγέθη.  Η μέτρηση ablation (AP-2 vs generic Karatsuba)
κατέδειξε $-\pct{8}$–$\pct{12}$ μείωση \instret αποκλειστικά από την
εξάλειψη runtime dispatch overhead.

\paragraph{Γενίκευση.}
Η αρχή εφαρμόζεται σε κάθε αλγόριθμο με compile-time-deterministic
recursion structure: NTT butterfly networks (σταθερό $\log_2 N$ βάθος),
FFT twiddle factor schedules, και Berlekamp-Massey iteration bounds
(σταθερό $2t$ iterations για γνωστό error-correction capability $t$).
Σε κάθε περίπτωση, η γνώση των παραμέτρων σε compile-time επιτρέπει
τη μετατροπή runtime decisions σε static code structure — μειώνοντας
τόσο τον αριθμό δυναμικών εντολών όσο και τη branch misprediction
pressure σε in-order pipelines.

Η σχεδιαστική επιλογή μεταξύ metaprogramming και hand-tuning εξαρτάται
από τη σταθερότητα των παραμέτρων: όταν οι παράμετροι είναι γνωστοί σε
compile-time (security levels, polynomial degrees), ο code generator
υπερτερεί.  Όταν οι παράμετροι εξαρτώνται από runtime context (μεταβλητό
μήκος μηνύματος, δυναμικό batch size), η generic VLA υλοποίηση παραμένει
η ορθή επιλογή.

%% --------------------------------------------------------------------------
\subsection{Σύνθεση: ISA Completeness υπερτερεί του ISA Width}
\label{ssec:principle-completeness}

Η συνδυαστική ανάλυση των τεσσάρων αρχών αποκαλύπτει ένα υπερκείμενο
εύρημα: η \defterm{πληρότητα} του ISA (παρουσία κατάλληλων domain-specific
εντολών) υπερτερεί του \defterm{εύρους} (αριθμός bits ανά vector register)
ως παράγοντας απόδοσης σε κρυπτογραφικά workloads.

Η τεκμηρίωση προέρχεται από δύο ανεξάρτητες παρατηρήσεις.  Πρώτον, η
μετάβαση Tier~1 → Tier~2 (προσθήκη \RVV χωρίς \Zvbc) παρέχει μόλις
$-\pct{8}$ μείωση \instret στο polymul — η vectorization των combine
loops ($\BigO{n}$ ανά level) δεν αντισταθμίζει τον scalar leaf bottleneck
($\BigO{n^2}$ ανά call).  Αντίθετα, η μετάβαση Tier~2 → Tier~3 (προσθήκη
\Zvbc) παρέχει $-\pct{59}$ — η vectorization του leaf μέσω \vclmul
εξαλείφει τον κυρίαρχο bottleneck.  Δεύτερον, η Keccak βελτιστοποίηση
μέσω \Zvbb (\insn{vror.vv}, \insn{vandn.vv}) παρέχει $-\pct{37}$ στον
Keccak πυρήνα — ενώ η αύξηση \VLEN από \num{256} σε \num{512} (διπλάσιο
εύρος, ίδιες εντολές) παρέχει μόλις $-\pct{4}$ στο πλήρες \KEM.

Η αρχή αυτή έχει άμεσες σχεδιαστικές συνέπειες για hardware architects:
η υλοποίηση \Zvbc/\Zvbb σε ένα core με $\VLEN = \num{256}$ παρέχει
μεγαλύτερο performance-per-area ratio από τη διπλασίαση του \VLEN σε
\num{512} χωρίς crypto extensions.  Η παρατήρηση αυτή ευθυγραμμίζεται
με τη φιλοσοφία του RVA23 profile, το οποίο καθιστά υποχρεωτικές τις
\Zvbb (vector bit-manipulation) αλλά δεν επιβάλλει ελάχιστο \VLEN πέραν
του \num{128}.

\section{Συγκριτική Αξιολόγηση Μεταγλωττιστών (Clang vs GCC)}
\label{sec:compiler-comparison}

Η ποιότητα του παραγόμενου κώδικα εξαρτάται κρίσιμα από τον μεταγλωττιστή,
ιδιαίτερα σε αρχιτεκτονικές με πρόσφατες extensions όπου τα compiler backends
βρίσκονται ακόμη σε ωρίμανση.  Η ενότητα αυτή αξιολογεί συστηματικά τους
δύο μεταγλωττιστές που χρησιμοποιήθηκαν στην παρούσα εργασία — Clang~21.1
(LLVM) και GCC~15.2 — μέσω ντετερμινιστικών μετρήσεων \instret στον
Spike \gls{iss}.  Η σύγκριση αποκαλύπτει ότι κανένας μεταγλωττιστής δεν
υπερτερεί καθολικά: η βέλτιστη επιλογή εξαρτάται από τον τύπο πυρήνα
και το tier υλοποίησης.

\subsection{Μεθοδολογία Σύγκρισης}
\label{ssec:compiler-methodology}

Κάθε variant μεταγλωττίστηκε με αμφότερους τους compilers σε τρία
επίπεδα βελτιστοποίησης (\code{-O2}, \code{-O3}, \code{-Os}) και
εκτελέστηκε στον Spike ISS.  Η μετρική σύγκρισης είναι ο ελάχιστος
\instret μεταξύ των τριών optimization levels — δηλαδή ο βέλτιστος
δυνατός κώδικας που παράγει κάθε compiler.  Η μεθοδολογία αυτή
εξαλείφει τον παράγοντα \q{λάθος flag} και εστιάζει στην εγγενή
ποιότητα codegen.

Η σύγκριση πραγματοποιήθηκε σε πλήρες \KEM (\KeyGen + \Encaps +
\Decaps) και όχι σε μεμονωμένους πυρήνες, ώστε να αποτυπωθεί η
αλληλεπίδραση μεταξύ inlining decisions, register allocation pressure,
και interprocedural optimization.  Τα αποτελέσματα αφορούν ταυτόσημο
πηγαίο κώδικα — η μόνη μεταβλητή είναι ο compiler.

\paragraph{Εύρημα 1: Ο GCC υπερτερεί στον scalar κώδικα.}

εντολές — η υπεροχή κυμαίνεται από \pct{1.2} (\code{ref\_vector}, L256)
έως \pct{22.6} (\code{karatsuba\_zbc}, L256).  Η εξήγηση βρίσκεται στη
δομή του hot path: ο πλήρως ξεδιπλωμένος scalar leaf (\code{clmul\_leaf\_n8})
αποτελεί ακολουθία \num{64} εντολών \clmul/\clmulh χωρίς control flow.
Ο GCC εκμεταλλεύεται αποδοτικότερα τους \num{31} διαθέσιμους GPRs μέσω
aggressive register coalescing, μειώνοντας τα stack spills στο αναδρομικό
Karatsuba tree.  Η διαφορά εντείνεται στο L256 ($N = \num{901}$ words)
όπου το βάθος αναδρομής αυξάνεται και η register pressure γίνεται κρίσιμη.

\paragraph{Εύρημα 2: Ο Clang υπερτερεί στον vector intrinsic κώδικα.}
Στο Tier~2 (\code{karatsuba\_rvv}), ο Clang κερδίζει στα L128 ($-\pct{2.8}$)
και L192 ($-\pct{1.3}$) — τα security levels όπου ο vector leaf
(\code{vclmul\_leaf}) κυριαρχεί στο instruction mix.  Η υπεροχή
αποδίδεται στην ωριμότερη υποστήριξη RVV intrinsics: ο Clang εκπέμπει
βέλτιστες \insn{vsetvli} ακολουθίες (αποφεύγοντας redundant
reconfigurations) και αξιοποιεί αποδοτικότερα τα vector register groups.
Η αντιστροφή στο L256 (GCC κερδίζει κατά \pct{24.7}) αντικατοπτρίζει
τη μεγαλύτερη αναλογία scalar Karatsuba overhead στο βαθύτερο recursion
tree — ο GCC ανακτά μέσω καλύτερου scalar scheduling.

\paragraph{Εύρημα 3: Αμεταβλητότητα ως προς optimization level.}
Μια αξιοσημείωτη παρατήρηση αφορά τη σταθερότητα του παραγόμενου κώδικα:
στα optimized variants (Tier~1–3), ο \instret παραμένει ταυτόσημος μεταξύ
\code{-O2}, \code{-O3}, και \code{-Os} εντός κάθε compiler.  Η εξήγηση
βρίσκεται στη δομή του πηγαίου κώδικα: ο code generator
(\code{gen\_karatsuba\_specialized.py}) εκπέμπει πλήρως εξειδικευμένες
συναρτήσεις με σταθερά loop bounds και compile-time-resolved offsets.
Ο compiler δεν έχει αποφάσεις βελτιστοποίησης να λάβει — ο κώδικας
είναι ήδη \q{pre-optimized} σε source level.  Η παρατήρηση αυτή
επιβεβαιώνει την αξία του metaprogramming
(βλ.\ \cref{ssec:principle-metaprogramming}): η εξειδίκευση σε source
level εξαλείφει την εξάρτηση από τον optimization level του compiler.

Η μόνη εξαίρεση εμφανίζεται στο Tier~0 (\code{ref\_scalar}), όπου ο
GCC παρουσιάζει σημαντική διακύμανση: \code{-O3} παράγει \cycles{113958344}
\instret (βέλτιστο), ενώ \code{-Os} παράγει \cycles{122366611} ($+\pct{7.4}$).
Η διαφορά αποδίδεται στο aggressive loop unrolling που εφαρμόζει ο
\code{-O3} στον bit-serial schoolbook πολλαπλασιασμό — ένα pattern που
δεν υπάρχει στα optimized variants λόγω της πλήρους εξειδίκευσης.

\subsection{Ασυμβατότητα GCC με \Zvbb Keccak Backend}
\label{ssec:gcc-zvbb-incompatibility}

Το Tier~3 (\code{karatsuba\_zvbc}) χρησιμοποιεί τον \Zvbb-accelerated
Keccak backend (\code{fips202\_zvbb\_x2.c}), ο οποίος δεν μεταγλωττίζεται
με GCC~15.2.  Δύο ανεξάρτητα ζητήματα εντοπίστηκαν κατά τη διερεύνηση.

\paragraph{Ζήτημα 1: Γλωσσική επέκταση sizeless types.}
Η x2 SoA αρχιτεκτονική δηλώνει πίνακες vector τύπων μέσω
\code{\_\_attribute\_\_((riscv\_rvv\_vector\_bits(N)))} — μια γλωσσική
επέκταση αποκλειστική του Clang.  Ο GCC ακολουθεί αυστηρά το RVV spec
και αντιμετωπίζει όλους τους RVV τύπους ως \defterm{sizeless} (scalable),
απορρίπτοντας τη δήλωση πινάκων σε compile-time.  Η ασυμβατότητα αυτή
δεν αποτελεί σφάλμα αλλά σχεδιαστική διαφωνία μεταξύ των δύο compilers
ως προς την ερμηνεία του RVV type system.

\paragraph{Ζήτημα 2: Codegen bug σε LMUL=8 \insn{vrgather.vv} + \insn{vror.vv}.}
Ακόμη και μετά την υλοποίηση GCC-compatible x2 path (flat \code{uint64\_t[50]}
buffer με named \code{vuint64m1\_t} locals), η single-stream
\code{KeccakF1600\_StatePermute} — η οποία χρησιμοποιεί LMUL=8
\insn{vrgather.vv} για τον $\pi$ step και \insn{vror.vv} (\Zvbb) για
τον $\rho$ step — παράγει κώδικα που εισέρχεται σε ατέρμονο βρόχο κατά
την εκτέλεση στον Spike.  Η ανάλυση του παραγόμενου assembly αποκάλυψε
ότι ο GCC~15.2 εκπέμπει μόλις \num{4} εντολές \insn{vrgather} (έναντι
\num{52} του Clang) και \num{1} εντολή \insn{vror.vv} (έναντι \num{42}),
υποδεικνύοντας σοβαρά ελαττωματική παραγωγή κώδικα για αυτό το pattern.
Η πιθανή αιτία εντοπίζεται στη register allocation: τα LMUL=8 register
groups καταναλώνουν και τους \num{32} vector registers ($4 \times 8 = 32$),
μη αφήνοντας χώρο για temporaries χωρίς spilling — και η λογική
spill/reload εμφανίζεται ελαττωματική.

\subsection{Ερμηνεία: Ωριμότητα Οικοσυστήματος}
\label{ssec:compiler-ecosystem-maturity}

Η ασυμβατότητα GCC με τον \Zvbb backend δεν αποτελεί αδυναμία της
αρχιτεκτονικής RISC-V — αντικατοπτρίζει τη χρονική υστέρηση του GCC
backend σε σχέση με τον LLVM στην υποστήριξη πρόσφατων vector crypto
extensions.  Η παρατήρηση αυτή εντάσσεται σε ευρύτερο μοτίβο: ο LLVM
αποτελεί τον de-facto reference compiler για RVV intrinsics (το RVV
Intrinsic Document αναπτύχθηκε εξαρχής έναντι του LLVM toolchain), ενώ
ο GCC ακολουθεί με καθυστέρηση 12–18 μηνών στην υποστήριξη νέων
extensions.

Η πρακτική συνέπεια για την παρούσα εργασία ήταν η υιοθέτηση
\defterm{dual-compiler workflow}: ο GCC χρησιμοποιήθηκε ως reference
compiler για KAT validation και scalar baseline, ενώ ο Clang
χρησιμοποιήθηκε για τα vector crypto kernels.  Η μεικτή μεταγλώττιση
(GCC framework + Clang kernels) είναι ασφαλής διότι αμφότεροι οι
compilers παράγουν συμβατά RISC-V ELF objects υπό το ίδιο \code{lp64d}
ABI.

Η κατάσταση αναμένεται να βελτιωθεί: η υποστήριξη \Zvbb στον GCC
βρίσκεται υπό ενεργή ανάπτυξη, και η ενσωμάτωση του
\code{riscv\_rvv\_vector\_bits} attribute αποτελεί ανοιχτή πρόταση στο
GCC bugzilla.  Η παρούσα εργασία τεκμηριώνει την κατάσταση κατά τον
χρόνο συγγραφής (Ιούνιος 2026) ως σημείο αναφοράς για μελλοντικές
αξιολογήσεις.

\subsection{Σύνοψη και Σχεδιαστική Σύσταση}
\label{ssec:compiler-summary}

Η συγκριτική αξιολόγηση αποκαλύπτει μια σαφή κατανομή ρόλων.  Ο GCC
υπερτερεί σε scalar-intensive κώδικα (Tier~0/1) χάρη σε ωριμότερη
register allocation για τον RISC-V integer register file.  Ο Clang
υπερτερεί σε vector intrinsic-heavy κώδικα (Tier~2/3) χάρη σε πληρέστερη
υποστήριξη RVV semantics και αποδοτικότερη \insn{vsetvli} emission.
Το Tier~3 αποτελεί αποκλειστικό πεδίο του Clang λόγω GCC codegen bugs
στο \Zvbb backend.

Η σχεδιαστική σύσταση για υλοποιήσεις \gls{pqc} σε RISC-V με vector
crypto extensions είναι τριπλή:

\begin{enumerate}
  \item Χρήση Clang ως primary compiler για vector crypto kernels —
    η υπεροχή σε RVV codegen και η αποκλειστική υποστήριξη \Zvbb
    καθιστούν τον LLVM μονόδρομο για Tier~3 υλοποιήσεις.
  \item Χρήση GCC ως cross-validation compiler για scalar paths —
    η ανεξάρτητη επιβεβαίωση ορθότητας μέσω δεύτερου compiler
    αυξάνει την εμπιστοσύνη στα αποτελέσματα.
  \item Αναφορά αποτελεσμάτων αμφότερων compilers όπου εφικτό —
    η διαφορά \instret μεταξύ compilers αποτελεί δημοσιεύσιμο δεδομένο
    που τεκμηριώνει την ωριμότητα του οικοσυστήματος.
\end{enumerate}

\section{Επαλήθευση Σταθερού Χρόνου Εκτέλεσης}
\label{sec:ct-verification}

Η επιτάχυνση κρυπτογραφικού κώδικα δεν έχει αξία εάν εισάγει πλευρικά
κανάλια χρονισμού (timing side-channels).  Η ενότητα αυτή τεκμηριώνει ότι
οι βελτιστοποιημένες υλοποιήσεις \HQC διατηρούν constant-time συμπεριφορά
— η εκτέλεσή τους είναι ανεξάρτητη από μυστικά δεδομένα.  Η στρατηγική
επαλήθευσης λειτουργεί σε δύο συμπληρωματικά στρώματα: στατική ανάλυση
μέσω ctgrind (Valgrind Memcheck) και στατιστική ανίχνευση διαρροής μέσω
dudect σε πραγματικό hardware.

%% --------------------------------------------------------------------------
\subsection{Μοντέλο Απειλής και Ορισμός Constant-Time}
\label{ssec:ct-threat-model}

Μια κρυπτογραφική υλοποίηση ικανοποιεί τη constant-time ιδιότητα όταν η
παρατηρήσιμη συμπεριφορά εκτέλεσης (χρονισμός, cache access patterns,
branch outcomes) είναι ανεξάρτητη από μυστικές εισόδους.  Για τον \HQC,
τα μυστικά δεδομένα περιλαμβάνουν το ιδιωτικό κλειδί
$\mathbf{sk} = (\mathbf{x}, \mathbf{y})$ (αραιά δυαδικά διανύσματα) και
το αποκρυπτογραφημένο μήνυμα $m'$ κατά τη διαδικασία decapsulation.

Τυπικά, μια υλοποίηση ικανοποιεί constant-time πειθαρχία όταν:
\begin{enumerate}
  \item κανένα conditional branch δεν εξαρτάται από μυστικά δεδομένα,
  \item καμία διεύθυνση load/store δεν εξαρτάται από μυστικά δεδομένα, και
  \item κάθε εκτελούμενη εντολή ανήκει στο Zkt subset — εντολές με
    αρχιτεκτονικά εγγυημένη σταθερή καθυστέρηση ανεξαρτήτως τιμών
    τελεστέων \cite{riscv-scalar-crypto-2022}.
\end{enumerate}

Η extension Zkt ορίζει τυπικά αυτή την εγγύηση: για κάθε εντολή
$i \in \mathcal{I}_{\mathrm{Zkt}}$ και οποιαδήποτε δύο ζεύγη τελεστέων
$x, y$ ίσου εύρους, υπό σταθερό μικροαρχιτεκτονικό context $\mu$, ισχύει
\begin{equation}
  T(i, x, \mu) = T(i, y, \mu).
  \label{eq:zkt-timing}
\end{equation}
Η ιδιότητα αυτή εξασφαλίζει ότι ο χρονισμός κάθε μεμονωμένης εντολής
δεν αποκαλύπτει πληροφορία για τα δεδομένα που επεξεργάζεται.

\paragraph{Ανάλυση κατά συνιστώσα.}
Δεν απαιτούν όλες οι συνιστώσες του \HQC decapsulation constant-time
υλοποίηση.  Η Fujisaki-Okamoto (FO) transform σχεδιάστηκε ώστε μόνο η
σύγκριση ciphertext και η επιλογή εξόδου να πρέπει να είναι constant-time
για τη διασφάλιση IND-CCA2 ασφάλειας.  Ο πολυωνυμικός πολλαπλασιασμός
(\code{vect\_mul}) επεξεργάζεται απευθείας το μυστικό κλειδί $\mathbf{y}$
και απαιτεί constant-time εκτέλεση.  Αντίθετα, η αποκωδικοποίηση
Reed-Muller/Reed-Solomon δύναται να είναι variable-time χωρίς να
παραβιάζεται η ασφάλεια — η FO transform μασκάρει τη χρονική πληροφορία
μέσω του re-encryption ελέγχου.  Ο Keccak/SHAKE είναι εγγενώς
constant-time λόγω αλγοριθμικής δομής: η permutation Keccak-f[1600]
αποτελείται αποκλειστικά από bitwise πράξεις (XOR, AND, NOT, ROT) χωρίς
data-dependent branches ή table lookups.

%% --------------------------------------------------------------------------
\subsection{Σχεδιαστικά Πρότυπα για CT Αριθμητική στο \texorpdfstring{$\GFpoly$}{GF(2)[x]}}
\label{ssec:ct-design-patterns}

Η constant-time ιδιότητα των βελτιστοποιημένων υλοποιήσεων δεν αποτελεί
τυχαίο αποτέλεσμα αλλά σχεδιαστική επιλογή σε τρία επίπεδα.

\paragraph{Hardware-guaranteed σταθερή καθυστέρηση (\Zbc).}
Οι εντολές \clmul/\clmulh της extension \Zbc παρέχουν carry-less
πολλαπλασιασμό με αρχιτεκτονικά εγγυημένη σταθερή καθυστέρηση (Zkt-compliant).
Η latency είναι ανεξάρτητη από τις τιμές τελεστέων — δεν υπάρχει
early-termination βελτιστοποίηση βασισμένη σε leading zeros.  Το αποτέλεσμα
είναι πάντοτε \num{128} bits ανεξαρτήτως μεγέθους εισόδου.

\paragraph{Ντετερμινιστική αναδρομή Karatsuba.}
Η αναδρομική δομή Karatsuba διαιρεί πολυώνυμα βάσει βαθμού (compile-time
σταθερά), ποτέ βάσει τιμών συντελεστών.  Το βάθος αναδρομής είναι σταθερό
για δεδομένο security level, δεν υπάρχει data-dependent early exit, και
κάθε leaf κλήση εκτελεί ταυτόσημη ακολουθία εντολών.  Ο πλήρως
ξεδιπλωμένος leaf (\code{clmul\_leaf\_n8}) εκτελεί \num{64} κλήσεις
\clmul/\clmulh με ντετερμινιστικό XOR assembly — μηδέν branches εντός
του hot path.

\paragraph{Vector carry-less multiply (\RVV + \Zvbc).}
Η υλοποίηση \code{karatsuba\_rvv} χρησιμοποιεί \vclmul/\vclmulh vector
εντολές.  Υπό Zkt, vector εντολές με ταυτόσημα \VLEN και \SEW
configurations έχουν σταθερή latency.  Η \RVV υλοποίηση χρησιμοποιεί
σταθερά \LMUL και element width για όλες τις πράξεις, επεξεργάζεται
polynomial limbs μέσω strided vector loads (address-independent), και
αποφεύγει \insn{vcompress} ή predicated operations σε μυστικά δεδομένα.
Η VLA δομή εγγυάται ότι η ροή ελέγχου εξαρτάται αποκλειστικά από δημόσιες
παραμέτρους (μέγεθος πολυωνύμου) ανεξαρτήτως του \VLEN που παρέχει το
hardware.

%% --------------------------------------------------------------------------
\subsection{Στατική Επαλήθευση: ctgrind (Valgrind Memcheck)}
\label{ssec:ct-ctgrind}

Η ctgrind μεθοδολογία αξιοποιεί τον Valgrind Memcheck ως εργαλείο
ανίχνευσης secret-dependent ροής ελέγχου.  Τα μυστικά δεδομένα
σημαίνονται ως \q{uninitialized} μέσω \code{VALGRIND\_MAKE\_MEM\_UNDEFINED},
και ο Memcheck αναφέρει κάθε conditional branch ή indexed memory access
που εξαρτάται από \q{uninitialized} bytes.

\paragraph{Ενσωμάτωση στο CI pipeline.}
Το workflow \code{ct-verify.yml} εκτελεί ctgrind για κάθε συνδυασμό
(security level $\times$ variant) σε κάθε push στο main branch.  Ο
harness (\code{ct\_harness.c}) ασκεί τη συνάρτηση \code{crypto\_kem\_dec()}
με τα bytes sigma (μυστικό fallback material) σημασμένα ως undefined.
Η επιλογή poisoning μόνο του sigma — αντί ολόκληρου του secret key —
αποφεύγει false positives από data-dependent loops στην ανακατασκευή
κλειδιού της reference υλοποίησης.

\paragraph{Αποτελέσματα.}
Η στατική επαλήθευση ολοκληρώνεται χωρίς violations σε όλα τα security
levels (128, 192, 256) για το \code{scalar\_ref} variant.  Ο Memcheck
δεν αναφέρει κανένα \q{Conditional jump depends on uninitialised value}
ούτε \q{Use of uninitialised value} — επιβεβαιώνοντας ότι η αλγοριθμική
δομή δεν περιέχει secret-dependent branches ή memory indexing.

\paragraph{Περιορισμοί.}
Η ctgrind παρουσιάζει τρεις δομικούς περιορισμούς.  Πρώτον, επαληθεύει
μόνο το \code{scalar\_ref} variant — τα RISC-V intrinsics δεν
μεταγλωττίζονται σε x86-64.  Δεύτερον, δεν ανιχνεύει μικροαρχιτεκτονικά
κανάλια χρονισμού (cache timing, pipeline effects, speculation).  Τρίτον,
υποθέτει ότι ο compiler δεν εισάγει CT violations κατά τη βελτιστοποίηση
— μια υπόθεση που δεν επαληθεύεται στατικά.  Παρ' όλα αυτά, ένα
\q{clean} αποτέλεσμα εγγυάται απουσία secret-dependent branches και loads
στα traced paths — ισχυρή ένδειξη αλγοριθμικής ορθότητας.

\subsection{Εμπειρική Επαλήθευση σε Hardware: Dudect (BPI-F3)}
\label{ssec:ct-dudect}

Η dudect μεθοδολογία \cite{Reparaz2017-dudect} αποτελεί εργαλείο
στατιστικής ανίχνευσης διαρροής βασισμένο στο Welch's t-test.  Οι
είσοδοι ταξινομούνται σε δύο κλάσεις:
\begin{itemize}
  \item \textbf{Class A (fixed):} η ίδια μυστική είσοδος επαναλαμβάνεται
    σε κάθε μέτρηση.
  \item \textbf{Class B (random):} νέα τυχαία είσοδος ανά μέτρηση.
\end{itemize}
Εάν η υλοποίηση είναι constant-time, οι κατανομές χρονισμού των δύο
κλάσεων είναι στατιστικά αδιάκριτες, παράγοντας $|t| < 4.5$ (threshold
που αντιστοιχεί σε $p < 6.8 \times 10^{-6}$, two-tailed).

\paragraph{Hardware target.}
Οι dudect harnesses εκτελούνται natively στο Banana Pi BPI-F3 (SpacemiT K1,
rv64gcv).  Ο χρονισμός μετράται μέσω \code{perf\_event\_open} hardware
counters (userspace-only cycles).  Η process isolation εξασφαλίζεται μέσω
\code{taskset -c 7} (CPU pinning σε isolated core), \code{nice -n -20}
(μέγιστη προτεραιότητα), και CPU governor κλειδωμένο σε \code{performance}
mode.  Όλα τα tests μεταγλωττίζονται με \code{-O3 -static}, ταυτόσημα
με το production optimization level.

\paragraph{Σχεδιαστική απόφαση: prepare-then-measure.}
Κατά την ανάπτυξη εντοπίστηκε ότι η naive interleaved προσέγγιση (παραγωγή
εισόδου → άμεση μέτρηση) εισάγει συστηματικό cache-state bias που παράγει
false positives ακόμη και σε γνωστά constant-time κώδικα
(βλ.\ \cref{ssec:ct-cache-bias}).  Η λύση ακολουθεί το canonical
prepare-then-measure pattern:
\begin{enumerate}
  \item \textbf{Phase 1 (Prepare):} παραγωγή όλων των εισόδων του batch
    σε pre-allocated buffers — αμφότερες οι κλάσεις γράφουν στην ίδια
    δομή buffer, εξασφαλίζοντας συμμετρική κατάσταση cache.
  \item \textbf{Phase 2 (Measure):} tight loop μέτρησης χωρίς κλήσεις
    \gls{prng} ή class-dependent branching εντός της χρονομετρούμενης
    περιοχής.
\end{enumerate}

\paragraph{Warm-up round.}
Πριν τον κύριο βρόχο μέτρησης, ένα πλήρες batch εκτελείται και
απορρίπτεται.  Η τεχνική αυτή εξαλείφει cold-start transients από
instruction cache misses, TLB fills, branch predictor training, και page
table walks — φαινόμενα που θα εισήγαγαν ασύμμετρη διακύμανση στα πρώτα
batches.

\paragraph{Percentile cropping (second-order test).}
Ο δεύτερος t-test εφαρμόζει percentile cropping: μετρήσεις πάνω από το
95ο εκατοστημόριο κάθε batch απορρίπτονται πριν τροφοδοτηθούν στον
t-test accumulator.  Η τεχνική αυτή αφαιρεί outliers από OS interrupts,
context switches, και DVFS transients που θα μασκάριζαν λεπτά σήματα
διαρροής.

input-dependent latency.  Ένα passing \code{dudect\_keccak} αποτέλεσμα
θα ήταν trivially αναμενόμενο χωρίς πρόσθετη πληροφοριακή αξία.

\subsection{Μεθοδολογικά Ευρήματα: Cache-State Bias και False Positives}
\label{ssec:ct-cache-bias}

Κατά την αρχική ανάπτυξη, ο dudect harness παρήγαγε false positives στη
vendor reference υλοποίηση (\code{ref\_scalar}) — κώδικα γνωστό ως
constant-time.  Η ανάλυση αιτίας αποκάλυψε συστηματική ασυμμετρία
κατάστασης cache μεταξύ των δύο κλάσεων.

Στη naive interleaved προσέγγιση, τα Class~B operands γράφονται από τον
\gls{prng} αμέσως πριν τη μέτρηση — θερμαίνοντας τις αντίστοιχες cache
lines στην L1d.  Τα Class~A operands (pre-generated, επαναχρησιμοποιούμενα)
ενδέχεται να είναι cold λόγω ενδιάμεσων evictions.  Ο t-test ανιχνεύει
ορθά μια χρονική διαφορά, η οποία όμως αντικατοπτρίζει cache miss patterns
αντί αλγοριθμικής εξάρτησης χρονισμού από μυστικά δεδομένα.

Η υιοθέτηση του canonical prepare-then-measure pattern (όπως στη reference
υλοποίηση των Reparaz et al.\ \cite{Reparaz2017-dudect}) εξαλείφει αυτό
το bias.  Αμφότερες οι κλάσεις γράφουν σε ταυτόσημες δομές buffer πριν
τον βρόχο μέτρησης, εξασφαλίζοντας συμμετρική κατάσταση cache.

Το εύρημα αυτό έχει μεθοδολογική σημασία για τη βιβλιογραφία: ένας dudect
harness που παράγει εισόδους inline με τις μετρήσεις δύναται να παράγει
false positives ακόμη και σε trivially constant-time κώδικα.  Ερευνητές
που υλοποιούν dudect-style tests πρέπει πάντοτε να επαληθεύουν τη
μεθοδολογία τους έναντι γνωστού CT baseline πριν εξάγουν συμπεράσματα
για την υπό εξέταση υλοποίηση.

Κανένα υπάρχον binary analysis framework δεν ερμηνεύει τις εντολές
\vclmul, \vclmulh, ή το vector-length-agnostic execution model
(strip-mining, \insn{vsetvli} state machine) που διέπει τη λειτουργία

VLA εκτέλεσης — τον \code{vtype} CSR, το δυναμικό \VLMAX, και τις
tail/mask agnostic πολιτικές.

Ο Valgrind (υποστήριξη RISCV64 από v3.25.0, Απρίλιος 2025
\cite{Valgrind-riscv64}) θα μπορούσε θεωρητικά να εκτελέσει ctgrind
natively στο BPI-F3.  Ωστόσο, ο instruction interpreter του Valgrind
δεν υποστηρίζει ακόμη \Zbc (carry-less multiply) ούτε \RVV vector
εντολές — κάθε binary που χρησιμοποιεί αυτές τις extensions τερματίζεται
με \q{unhandled instruction bytes}.  Ο περιορισμός αυτός περιορίζει τον
on-target Valgrind στο \code{ref\_scalar} variant — ακριβώς αυτό που
ήδη επαληθεύεται μέσω ctgrind σε x86 στο CI.

Η εμπειρική dudect μεθοδολογία αποτελεί state-of-the-art για αυτές τις
νέες ISA extensions.  Η προσέγγιση αυτή ακολουθεί τη μεθοδολογία του
pqm4 project \cite{pqm4} (Valgrind on host + timing on Cortex-M4) —
αναγνωρισμένη πρακτική στην κοινότητα \gls{pqc} benchmarking.

%% --------------------------------------------------------------------------
\subsection{Ερμηνεία Αποτελεσμάτων: Τι Αποδεικνύει και Τι Δεν Αποδεικνύει
  η Dudect}
\label{ssec:ct-interpretation}

Ένα passing dudect αποτέλεσμα δεν αποτελεί μαθηματική απόδειξη
constant-time συμπεριφοράς.  Σημαίνει ότι στο δεδομένο measurement budget
($N_{\max}$) και confidence level ($|t| < 4.5$), δεν παρατηρήθηκε
στατιστικά σημαντική συσχέτιση χρονισμού με μυστικά δεδομένα.  Τρεις
caveats πρέπει να αναγνωριστούν ρητά:
\begin{itemize}
  \item Διαρροή κάτω από το sensitivity threshold (καθοριζόμενο από
    $N_{\max}$, noise floor, και effect size) δεν θα ανιχνευόταν.
  \item Διαφορετικό input class partitioning ενδέχεται να αποκαλύψει
    διαρροή που το \q{fixed vs random} δεν εντοπίζει.
  \item Μικροαρχιτεκτονικά φαινόμενα πολύ χαμηλής πιθανότητας (σπάνια
    TLB conflict patterns) ενδέχεται να απαιτούν περισσότερες μετρήσεις.
\end{itemize}

Αντίστροφα, ένα failing αποτέλεσμα ($|t| > 4.5$) αποτελεί ισχυρό θετικό
δείκτη — false positives με $|t| > 4.5$ είναι αστρονομικά απίθανα υπό
τη μηδενική υπόθεση ($p < 6.8 \times 10^{-6}$).  Η ασυμμετρία αυτή
καθιστά τη dudect ιδιαίτερα αξιόπιστη ως εργαλείο ανίχνευσης (detection)
— λιγότερο ως εργαλείο απόδειξης απουσίας (proof of absence).

Το multi-run protocol (N$=$10 ανεξάρτητα trials με διαφορετικά seeds)
ενισχύει την τεκμηρίωση επιδεικνύοντας συνέπεια μεταξύ ανεξάρτητων
πειραμάτων.  Εάν \num{10} runs με διαφορετικά \gls{prng} seeds περνούν
στις \num{100000} μετρήσεις έκαστο, η συνδυασμένη εμπιστοσύνη υπερβαίνει
σημαντικά οποιοδήποτε μεμονωμένο run.

Η formal CT verification για RISC-V binaries με Vector και Vector Crypto
extensions παραμένει ανοιχτό ερευνητικό πρόβλημα.  Η ανάπτυξη
σημασιολογικών μοντέλων για \RVV/\Zvbc σε binary analysis frameworks
αποτελεί σημαντική μελλοντική ερευνητική κατεύθυνση για την κοινότητα
κρυπτογραφικής μηχανικής RISC-V (βλ.\ \cref{sec:future-work}).

\paragraph{Σύνοψη ασφάλειας.}
Η βελτιστοποιημένη υλοποίηση \HQC διατηρεί constant-time συμπεριφορά σε
όλα τα optimized variants (\code{karatsuba\_zbc}, \code{karatsuba\_rvv})
και σε όλα τα security levels (128, 192, 256), όπως τεκμηριώνεται μέσω:
(α)~αρχιτεκτονικής ανάλυσης — όλες οι εντολές ανήκουν στο Zkt-compliant
subset χωρίς secret-dependent control flow ή memory addressing,
(β)~στατικής επαλήθευσης — ctgrind περνά χωρίς violations (CI-automated),
και (γ)~εμπειρικής hardware επαλήθευσης — dudect περνά στο BPI-F3 με
t-statistics πολύ κάτω από το detection threshold.  Τα performance gains
μέσω Karatsuba recursion, \Zbc carry-less multiply, και \RVV vectorization
δεν παραβιάζουν την timing-side-channel αντοχή που απαιτείται για
μετα-κβαντικές \KEM deployments.
