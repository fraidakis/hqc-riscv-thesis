\section{Σχεδιαστικές Αρχές και Βασική Αρχιτεκτονική RV64}
\label{sec:rv64-design}

Η ενότητα αυτή παρουσιάζει τις θεμελιώδεις σχεδιαστικές αρχές της
αρχιτεκτονικής RISC-V, τα βασικά χαρακτηριστικά του base integer \gls{isa}
RV64I, τη σύμβαση ονοματοδοσίας επεκτάσεων, και τη σύγκριση σχεδιαστικής
φιλοσοφίας με τις κυρίαρχες εμπορικές αρχιτεκτονικές.

\subsection{Ιστορικό Πλαίσιο και Φιλοσοφία}
\label{ssec:riscv-history}

Η αρχιτεκτονική RISC-V αναπτύχθηκε το 2010 στο Parallel Computing Laboratory
(Par Lab) του Πανεπιστημίου της Καλιφόρνιας στο Berkeley, από τον καθηγητή
Krste Asanović και τους μεταπτυχιακούς φοιτητές Andrew Waterman και Yunsup
Lee~\cite{Waterman2011-riscv}. Η αρχική κινητήρια δύναμη ήταν πρακτική: η
ανάγκη για ένα \gls{isa} κατάλληλο τόσο για εκπαίδευση όσο και για έρευνα,
χωρίς τους νομικούς περιορισμούς (licensing fees, NDA requirements) που
συνοδεύουν τα εμπορικά ISA. Η ονομασία \q{RISC-V} αντικατοπτρίζει τη θέση
του ως πέμπτης γενιάς RISC αρχιτεκτονικών που αναπτύχθηκαν στο Berkeley,
μετά τα RISC-I (1981), RISC-II, SOAR και SPUR~\cite{Patterson2017-COD}.

\paragraph{Θεμελιώδεις σχεδιαστικές αρχές.}
Τρεις αρχές διαφοροποιούν το RISC-V από τα προγενέστερα ακαδημαϊκά και
εμπορικά ISA. Πρώτον, η αρχή \defterm{minimal base + optional extensions}:
το base ISA (RV32I ή RV64I) περιέχει μόνο τις ελάχιστες εντολές που
απαιτούνται για γενικό υπολογισμό, ενώ κάθε πρόσθετη λειτουργικότητα
(πολλαπλασιασμός, floating-point, atomics, vector) παρέχεται μέσω
προαιρετικών, ανεξάρτητα τυποποιημένων επεκτάσεων. Αυτή η modular δομή
επιτρέπει σε σχεδιαστές υλικού να υλοποιήσουν μόνο τις επεκτάσεις που
απαιτεί η εφαρμογή τους — από μικροελεγκτές IoT (RV32I μόνο) έως
επεξεργαστές κέντρων δεδομένων (RV64GCV με πλήρεις κρυπτογραφικές
επεκτάσεις). Δεύτερον, η αρχή του \defterm{ανοιχτού ISA}: η προδιαγραφή
διατίθεται χωρίς royalties ή licensing fees υπό ανοιχτή άδεια, εξαλείφοντας
τα εμπόδια εισόδου για ακαδημαϊκούς, startups και κυβερνητικούς οργανισμούς.
Τρίτον, η αρχή της \defterm{σταθερότητας}: το base ISA παγώνει μετά την
τυποποίηση (ratification) — νέα λειτουργικότητα προστίθεται αποκλειστικά μέσω
νέων extensions, χωρίς τροποποίηση υπαρχόντων εντολών.

\paragraph{Σημασία για κρυπτογραφικές εφαρμογές.}
Η modular φιλοσοφία του RISC-V αποκτά ιδιαίτερη σημασία στο πλαίσιο της
μετα-κβαντικής κρυπτογραφίας. Η ικανότητα προσθήκης νέων κρυπτογραφικών
επεκτάσεων χωρίς τροποποίηση του base ISA σημαίνει ότι η αρχιτεκτονική
μπορεί να εξελίσσεται παράλληλα με τις αλγοριθμικές ανάγκες — ακριβώς η
κρυπτογραφική ευελιξία που τεκμηριώθηκε ως απαίτηση
στην~\cref{ssec:agility-requirement}. Η απουσία vendor lock-in εγγυάται ότι
κώδικας γραμμένος για τυποποιημένες επεκτάσεις (π.χ.\ \gls{zbc}, \gls{zvbc}) εκτελείται
σε οποιαδήποτε συμβατή υλοποίηση, ανεξαρτήτως κατασκευαστή. Ο οργανισμός
RISC-V International, που ιδρύθηκε το 2015, διαχειρίζεται τη διαδικασία
τυποποίησης και διασφαλίζει τη συμβατότητα μεταξύ υλοποιήσεων μέσω
compliance test suites.

\subsection{Βασικά Χαρακτηριστικά RV64I}
\label{ssec:rv64i-features}

Το RV64I αποτελεί το base integer \gls{isa} για εφαρμογές 64-bit και ορίζει
τη θεμελιώδη αρχιτεκτονική κατάσταση (architectural state) και το σύνολο
εντολών πάνω στο οποίο δομούνται όλες οι επεκτάσεις~\cite{RISCV-unpriv2024}.
Τα βασικά χαρακτηριστικά του περιγράφονται στις ακόλουθες παραγράφους.

\paragraph{Αρχιτεκτονική κατάσταση.}
Το RV64I ορίζει \num{32} \glspl{gpr} πλάτους 64~bit, με ονομασίες
\code{x0}–\code{x31}. Ο καταχωρητής \code{x0} είναι σταθερά μηδέν
(hardwired zero) — κάθε εγγραφή σε αυτόν απορρίπτεται, ενώ κάθε ανάγνωση
επιστρέφει μηδέν. Αυτή η σχεδιαστική επιλογή απλοποιεί τη σύνθεση σύνθετων
λειτουργιών: η εντολή \insn{addi x5, x0, 42} υλοποιεί φόρτωση σταθεράς
(load immediate), η \insn{add x0, x0, x0} υλοποιεί NOP, και η
\insn{sub x5, x0, x6} υλοποιεί αρνητικοποίηση (negate). Ο program counter
(PC) αποτελεί ξεχωριστό αρχιτεκτονικό καταχωρητή πλάτους 64~bit, μη
προσβάσιμο ως \gls{gpr}.

\paragraph{Μοντέλο μνήμης και εντολές πρόσβασης.}
Το RISC-V ακολουθεί αυστηρό \defterm{load-store μοντέλο}: αριθμητικές και
λογικές πράξεις εκτελούνται αποκλειστικά μεταξύ καταχωρητών, ενώ η μνήμη
προσπελαύνεται μόνο μέσω εξειδικευμένων εντολών load (\insn{ld}, \insn{lw},
\insn{lh}, \insn{lb}) και store (\insn{sd}, \insn{sw}, \insn{sh}, \insn{sb}).
Αυτός ο διαχωρισμός απλοποιεί τον σχεδιασμό pipeline, καθώς μόνο ένα στάδιο
(memory stage) χρειάζεται πρόσβαση στη μνήμη. Ο χώρος διευθύνσεων είναι
επίπεδος (flat), byte-addressable, με little-endian byte ordering ως
προεπιλογή.

\paragraph{Κωδικοποίηση εντολών.}
Κάθε εντολή RV64I έχει σταθερό μήκος \num{32}~bit, οργανωμένη σε έξι
βασικές μορφές (instruction formats): R-type (register-register), I-type
(immediate), S-type (store), B-type (branch), U-type (upper immediate) και
J-type (jump). Η \cref{fig:rv64-formats} παρουσιάζει τη δομή κάθε μορφής.
Η σταθερή θέση των πεδίων \code{rs1}, \code{rs2} και \code{rd} σε όλες τις
μορφές (bits 19:15, 24:20 και 11:7 αντίστοιχα) επιτρέπει στο υλικό να
ξεκινήσει ανάγνωση του register file πριν ολοκληρωθεί η αποκωδικοποίηση
εντολής — κρίσιμη βελτιστοποίηση για pipelined υλοποιήσεις.

\paragraph{Επίπεδα προνομίων.}
Η αρχιτεκτονική RISC-V ορίζει τρία επίπεδα προνομίων (privilege levels):
Machine mode (M-mode), Supervisor mode (S-mode) και User mode (U-mode). Το
M-mode αποτελεί το υψηλότερο επίπεδο προνομίων και είναι το μοναδικό
υποχρεωτικό — μια ελάχιστη υλοποίηση RISC-V μπορεί να υποστηρίζει μόνο
M-mode. Η παρούσα εργασία εκτελεί αποκλειστικά σε M-mode (bare-metal), χωρίς
λειτουργικό σύστημα, εξασφαλίζοντας πλήρη πρόσβαση σε \glspl{csr} μέτρησης
απόδοσης (\code{mcycle}, \code{minstret}) και απουσία OS jitter στις μετρήσεις
(βλ.~\cref{sec:measurement-purity}).

\subsection{Σύμβαση Ονοματοδοσίας Επεκτάσεων και Standard Profiles}
\label{sec:extension-naming}

Η modular δομή του RISC-V απαιτεί μια συστηματική σύμβαση ονοματοδοσίας για
τον προσδιορισμό του ακριβούς συνόλου επεκτάσεων που υποστηρίζει μια
υλοποίηση. Η σύμβαση αυτή κωδικοποιείται στο \defterm{ISA string} — μια
συμβολοσειρά που περιγράφει πλήρως τις δυνατότητες ενός
επεξεργαστή~\cite{RISCV-unpriv2024}.

\paragraph{Δομή ISA string.}
Ένα ISA string ακολουθεί τη μορφή \code{RV\{XLEN\}\{base\}\_\{extensions\}},
όπου \code{XLEN} είναι το πλάτος καταχωρητών (32 ή 64), \code{base} είναι
το base ISA (I), και \code{extensions} είναι η λίστα ενεργών επεκτάσεων. Η
συντομογραφία \code{G} (General) αντιστοιχεί στο σύνολο
\code{IMAFD} — δηλαδή base integer, πολλαπλασιασμός/διαίρεση, atomics,
single-precision floating-point και double-precision floating-point. Η
επέκταση \code{C} (Compressed) προσθέτει 16-bit εντολές για μείωση code
density. Κατά συνέπεια, η συντομογραφία \code{RV64GC} αντιστοιχεί στο
πλήρες \code{RV64IMAFDC} — το ελάχιστο σύνολο για γενικού σκοπού εφαρμογές
64-bit.

οργανισμό RISC-V International, εγγυώντας σταθερότητα και διαλειτουργικότητα
μεταξύ υλοποιήσεων. Τα ISA strings που χρησιμοποιούνται στη μεταγλώττιση

\paragraph{Standard Profiles και mainstream adoption.}
Η ύπαρξη πολλαπλών προαιρετικών επεκτάσεων δημιουργεί κίνδυνο
κατακερματισμού του οικοσυστήματος: αν κάθε υλοποίηση επιλέγει διαφορετικό
υποσύνολο, η φορητότητα λογισμικού υπονομεύεται. Τα \defterm{Standard
Profiles} αντιμετωπίζουν αυτό το πρόβλημα ορίζοντας υποχρεωτικά σύνολα
επεκτάσεων για συγκεκριμένες κατηγορίες εφαρμογών. Το προφίλ
RVA23~\cite{RVA23-profile}, που τυποποιήθηκε τον Οκτώβριο 2024, ορίζει τις
απαιτήσεις για επεξεργαστές εφαρμογών 64-bit — αποτελεί προϋπόθεση για το
Android RISC-V ABI και στοχεύεται από κάθε σημαντικό κατασκευαστή
επεξεργαστών RISC-V.

Η \cref{tab:rva23-extensions} παρουσιάζει τη σχέση μεταξύ των επεκτάσεων που

\paragraph{Concrete hardware: SpacemiT K1 X60.}
Ως συγκεκριμένο παράδειγμα RVA22-compliant hardware, ο επεξεργαστής SpacemiT K1
X60 (Banana Pi BPI-F3) υλοποιεί RV64GCVB με \VLEN $= \num{256}$~bits και
dual-issue in-order pipeline. Η πλατφόρμα αυτή χρησιμοποιείται στην παρούσα
εργασία ως hardware validation platform για επικύρωση των αποτελεσμάτων σε
πραγματικό silicon (λεπτομέρειες στην~\cref{ssec:bpi-f3}). Ο K1 X60 υποστηρίζει
εγγενώς τις scalar επεκτάσεις (\gls{zbc}, \gls{zbb}) και τη διανυσματική μονάδα \RVV~1.0,
καλύπτοντας πλήρως τα Tier~1 και Tier~2 variants, αλλά δεν υλοποιεί τις
Vector-Crypto επεκτάσεις \gls{zvbc} και \gls{zvbb} — αυτές απαιτούν συμμόρφωση με το
προφίλ RVA23, το οποίο δεν είναι ακόμη διαθέσιμο σε silicon. Η ύπαρξη
εμπορικού hardware που υποστηρίζει τις επεκτάσεις Tier~1 και Tier~2 επιβεβαιώνει
ότι η προσέγγιση της παρούσας εργασίας δεν αποτελεί θεωρητική άσκηση αλλά
στοχεύει ήδη διαθέσιμες πλατφόρμες.

\paragraph{Κωδικοποίηση και decode complexity.}
Η σταθερή κωδικοποίηση 32-bit του RISC-V (και του ARM) απλοποιεί δραστικά
τη λογική αποκωδικοποίησης σε σχέση με τη μεταβλητού μήκους κωδικοποίηση του
x86 (1–15 bytes ανά εντολή). Σε pipelined υλοποιήσεις, η σταθερή
κωδικοποίηση εξαλείφει την ανάγκη pre-decode σταδίου για τον προσδιορισμό
ορίων εντολών, μειώνοντας τόσο την κατανάλωση ενέργειας όσο και τον χρόνο
κύκλου. Η επέκταση C (Compressed) του RISC-V προσθέτει 16-bit εντολές για
βελτίωση code density χωρίς να επηρεάζει τη βασική decode λογική — οι
compressed εντολές αποσυμπιέζονται σε πλήρεις 32-bit εντολές στο πρώτο
στάδιο pipeline.

\paragraph{Μοντέλο κρυπτογραφικής υποστήριξης.}
Οι τρεις αρχιτεκτονικές ακολουθούν θεμελιωδώς διαφορετικές φιλοσοφίες στην
υποστήριξη κρυπτογραφικών πράξεων. Η ARM παρέχει \defterm{dedicated
macro-operations}: εντολές όπως η EOR3 (τριπλό XOR), η RAX1 (rotate-and-XOR)
και η BCAX (bit-clear-and-XOR) σχεδιάστηκαν αποκλειστικά για τα βήματα θ, ρ
και χ του Keccak~\cite{RISCV-crypto-spec}. Αυτές οι εντολές μεγιστοποιούν
την απόδοση για τον συγκεκριμένο αλγόριθμο αλλά δεν εξυπηρετούν άλλες
εφαρμογές. Η x86-64 παρέχει \defterm{wide SIMD}: η εντολή
\insn{vpclmulqdq} εκτελεί carry-less multiplication σε 512-bit ZMM
registers, επεξεργαζόμενη \num{8} ζεύγη 64-bit πολυωνύμων ταυτόχρονα — αλλά
απαιτεί σταθερό πλάτος register file και δεν κλιμακώνεται σε μικρότερες
υλοποιήσεις.

Το RISC-V ακολουθεί μια ενδιάμεση προσέγγιση: \defterm{γενικού σκοπού
κρυπτογραφικές extensions}. Η εντολή \clmul εκτελεί carry-less
multiplication — χρήσιμη τόσο στον \gls{hqc} (πολυωνυμικός πολλαπλασιασμός σε
$\GF{2}[x]$) όσο και σε GCM, CRC, GHASH και Barrett reduction. Η εντολή
\vror εκτελεί vector rotation — χρήσιμη τόσο στον Keccak (βήμα ρ) όσο και
σε ChaCha20, BLAKE3 και γενικό bit-manipulation. Αυτή η φιλοσοφία θυσιάζει
μέρος της peak single-operation απόδοσης (μία \insn{EOR3} αντικαθιστά τρεις
\insn{vxor}) αλλά παρέχει ευρύτερη αξιοποίηση του πυριτίου και πλήρη
κρυπτογραφική ευελιξία.

\paragraph{Vector μοντέλο: VLA έναντι σταθερού πλάτους.}
Η πλέον σημαντική αρχιτεκτονική διαφορά για τη βελτιστοποίηση κρυπτογραφικών
πυρήνων αφορά το vector μοντέλο. Η x86-64 χρησιμοποιεί σταθερού πλάτους SIMD
registers (128-bit XMM, 256-bit YMM, 512-bit ZMM) — ο κώδικας γράφεται για
συγκεκριμένο πλάτος και απαιτεί rewrite για αξιοποίηση ευρύτερων registers.
Η ARM NEON χρησιμοποιεί επίσης σταθερό πλάτος (128-bit), ενώ η νεότερη SVE
υιοθετεί VLA μοντέλο (128–2048 bit) παρόμοιο με το RVV.

Το RISC-V \RVV ακολουθεί πλήρως \gls{vla} σχεδιασμό: ο ίδιος κώδικας
εκτελείται σε οποιοδήποτε \VLEN χωρίς recompilation. Ο μηχανισμός
\insn{vsetvl} (βλ.~\cref{sec:rvv-architecture}) ρυθμίζει δυναμικά τον αριθμό
στοιχείων ανά vector operation βάσει του hardware \VLEN. Αυτό σημαίνει ότι
κώδικας γραμμένος σήμερα για \VLEN=256 θα αξιοποιήσει αυτόματα μελλοντικό
υλικό με \VLEN=512 ή \VLEN=1024 — χωρίς τροποποίηση πηγαίου κώδικα. Η
ανάλυση κλιμάκωσης ως προς \VLEN παρουσιάζεται στο \cref{ch:results}.

\paragraph{Συνέπειες για την παρούσα εργασία.}
Η σύγκριση αναδεικνύει τη θέση του RISC-V ως πλατφόρμας που συνδυάζει
αρχιτεκτονική καθαρότητα (σταθερή κωδικοποίηση, load-store μοντέλο, VLA
vectors) με πρακτική ευελιξία (ανοιχτό licensing, modular extensions,
mainstream adoption path). Η απόδοση σε κρυπτογραφικές εφαρμογές εξαρτάται
λιγότερο από peak single-instruction throughput και περισσότερο από την
ικανότητα αξιοποίησης εξειδικευμένων εντολών (\clmul, \vclmul, \vror) σε
αλγοριθμικά κρίσιμα σημεία — ακριβώς η προσέγγιση που ακολουθεί η παρούσα
εργασία. Η αναλυτική παρουσίαση αυτών των εντολών ακολουθεί στις
επόμενες ενότητες.

\section{Scalar Κρυπτογραφικές Επεκτάσεις (\Zbc, \Zbb, Zbkb)}
\label{sec:scalar-extensions}

Η ενότητα αυτή παρουσιάζει τις scalar κρυπτογραφικές επεκτάσεις που αξιοποιεί
η παρούσα εργασία στο Tier~1 profile. Οι επεκτάσεις αυτές παρέχουν
εντολές bit-manipulation και carry-less multiplication που αντιστοιχούν άμεσα
σε θεμελιώδεις κρυπτογραφικές πράξεις — πολυωνυμικό πολλαπλασιασμό σε
$\GFpoly$, rotations για Keccak, και byte-level μετασχηματισμούς.

\subsection{Η Επέκταση \Zbc: Carry-Less Multiplication}
\label{ssec:zbc-extension}

Η επέκταση \gls{zbc} (Carry-less multiplication), τυποποιημένη τον Νοέμβριο
2021~\cite{RISCV-bitmanip-spec}, ορίζει τρεις εντολές που εκτελούν
πολλαπλασιασμό χωρίς κρατούμενο (carry-less multiplication) μεταξύ δύο
64-bit τελεστέων:

\begin{itemize}
  \item \clmul~\code{rd, rs1, rs2}: υπολογίζει τα κάτω 64~bit του
    128-bit carry-less γινομένου $\text{rs1} \polymul \text{rs2}$.
  \item \clmulh~\code{rd, rs1, rs2}: υπολογίζει τα άνω 64~bit του
    ίδιου γινομένου.
  \item \insn{clmulr}~\code{rd, rs1, rs2}: υπολογίζει το reversed
    carry-less product (χρήσιμο σε CRC αλλά μη αξιοποιούμενο στην
    παρούσα εργασία).
\end{itemize}

\paragraph{Σημασιολογία carry-less multiplication.}
Η πράξη carry-less multiplication (ή polynomial multiplication)
διαφέρει από τον ακέραιο πολλαπλασιασμό σε ένα κρίσιμο σημείο: η πρόσθεση
μερικών γινομένων εκτελείται μέσω XOR αντί αριθμητικής πρόσθεσης, εξαλείφοντας
τη διάδοση κρατουμένου. Μαθηματικά, αν $a(x) = \sum_{i=0}^{63} a_i x^i$ και
$b(x) = \sum_{j=0}^{63} b_j x^j$ είναι πολυώνυμα σε $\GFpoly$ αναπαριστώμενα
ως 64-bit λέξεις, τότε:
\begin{equation}
  c(x) = a(x) \cdot b(x) = \sum_{k=0}^{126} c_k x^k, \quad
  c_k = \bigoplus_{\substack{i+j=k \\ 0 \leq i,j \leq 63}} a_i \cdot b_j.
  \label{eq:clmul-definition}
\end{equation}
Το αποτέλεσμα είναι πολυώνυμο βαθμού $\leq 126$, αναπαριστώμενο σε 128~bit.
Η \cref{fig:clmul-semantics} απεικονίζει τη διαδικασία σε μικρό μέγεθος
(4~bit), αναδεικνύοντας τη θεμελιώδη διαφορά από τον ακέραιο
πολλαπλασιασμό: τα μερικά γινόμενα συνδυάζονται αποκλειστικά μέσω XOR.

  \centering
  \input{figures/ch3-riscv/clmul-semantics.tex}
  \caption{Σημασιολογία carry-less multiplication σε $\GFpoly$. Τα μερικά
    γινόμενα (shifted copies του $a(x)$, gated από τα bits του $b(x)$)
    συνδυάζονται μέσω XOR χωρίς διάδοση κρατουμένου — σε αντίθεση με τον
    ακέραιο πολλαπλασιασμό όπου η πρόσθεση παράγει carries.}
  \label{fig:clmul-semantics}
\end{figure}

\paragraph{Αντιστοίχιση σε κρυπτογραφικά primitives.}
Η carry-less multiplication αποτελεί τη θεμελιώδη πράξη σε πολλαπλά
κρυπτογραφικά πρωτόκολλα. Στο \gls{hqc}, ο πολυωνυμικός πολλαπλασιασμός σε
$\GF{2}[x]/(x^N - 1)$ αποτελεί τον κυρίαρχο υπολογιστικό πυρήνα
(βλ.~\cref{sec:polymul-theory}). Πέραν του \gls{hqc}, η ίδια πράξη χρησιμοποιείται
στο GCM (Galois/Counter Mode) για τον υπολογισμό GHASH, στον υπολογισμό CRC
(Cyclic Redundancy Check), και στη Barrett reduction σε δυαδικά
πεδία~\cite{RISCV-crypto-spec}. Η γενικότητα αυτή επιβεβαιώνει τη
σχεδιαστική φιλοσοφία του RISC-V: μία εντολή εξυπηρετεί πολλαπλούς
αλγορίθμους, σε αντίθεση με dedicated macro-operations που στοχεύουν
αποκλειστικά έναν αλγόριθμο.

\paragraph{Ποσοτική επίπτωση: before/after σύγκριση.}
Χωρίς hardware carry-less multiply, ο πολλαπλασιασμός δύο 64-bit πολυωνύμων
απαιτεί έναν βρόχο \num{64} επαναλήψεων: σε κάθε επανάληψη εξάγεται ένα bit
του δεύτερου τελεστέου, δημιουργείται μάσκα, εκτελείται conditional XOR του
ολισθημένου πρώτου τελεστέου, και ενημερώνεται ο συσσωρευτής. Η διαδικασία
απαιτεί περίπου \num{640} εντολές ανά 64-bit γινόμενο (10 εντολές ανά
επανάληψη $\times$ 64 επαναλήψεις). Με τη \gls{zbc}, το ίδιο αποτέλεσμα
παράγεται σε ακριβώς \num{2} εντολές: \clmul (κάτω 64~bit) και \clmulh
(άνω 64~bit). Η μείωση ανέρχεται σε \speedup{320} σε instruction count
ανά στοιχειώδες γινόμενο — μια μετάβαση που μετασχηματίζει τον πολυωνυμικό
πολλαπλασιασμό από compute-bound σε memory-bound πρόβλημα.

Η \cref{fig:clmul-before-after} παρουσιάζει τη σύγκριση σε επίπεδο assembly:
αριστερά ο naive shift-and-XOR βρόχος, δεξιά το ζεύγος \clmul/\clmulh.

  \centering
  \input{figures/ch3-riscv/clmul-before-after.tex}
  \caption{Σύγκριση assembly για πολλαπλασιασμό 64-bit πολυωνύμων σε

\paragraph{Χρήση μέσω C intrinsics.}
Η πρόσβαση στις εντολές \gls{zbc} γίνεται μέσω των compiler intrinsics
\code{\_\_riscv\_clmul\_64(a, b)} και \code{\_\_riscv\_clmulh\_64(a, b)},
ορισμένων στο header \code{<riscv\_bitmanip.h>}. Τα intrinsics συμμετέχουν
πλήρως στο optimization pipeline του compiler (register allocation,
instruction scheduling, CSE), σε αντίθεση με inline assembly που αποτελεί
αδιαφανές block. Η παρούσα εργασία χρησιμοποιεί αποκλειστικά intrinsics για
τις εντολές \gls{zbc} — η αρχική υλοποίηση μέσω inline assembly αντικαταστάθηκε
κατά τη φάση βελτιστοποίησης (βλ.~\cref{sec:polymul-scalar}).

\paragraph{Δευτερεύουσα χρήση: αριθμητική $\GF{2^8}$.}
Πέραν του πολυωνυμικού πολλαπλασιασμού μεγάλων πολυωνύμων, η \clmul
αξιοποιείται και στην αριθμητική $\GF{2^8}$ που απαιτεί ο αποκωδικοποιητής
Reed-Solomon (βλ.~\cref{sec:ecc-theory}). Ο πολλαπλασιασμός δύο
στοιχείων $a, b \in \GF{2^8}$ υπολογίζεται ως carry-less product ακολουθούμενο
από modular reduction ως προς το αναγωγικό πολυώνυμο $x^8 + x^4 + x^3 + x + 1$.
Η \clmul υπολογίζει το 16-bit γινόμενο σε μία εντολή (αντί \num{56} εντολών
στον software βρόχο της reference υλοποίησης), ενώ η reduction εκτελείται σε
σταθερό αριθμό shift-and-XOR πράξεων.

\subsection{Η Επέκταση \Zbb: Basic Bit-Manipulation}
\label{ssec:zbb-extension}

Η επέκταση \gls{zbb} (Basic bit-manipulation), τυποποιημένη τον Νοέμβριο
2021~\cite{RISCV-bitmanip-spec}, παρέχει εντολές bit-level χειρισμού που
εξαλείφουν σύνθετες ακολουθίες βασικών εντολών. Οι εντολές με κρυπτογραφική
σημασία για την παρούσα εργασία είναι:

\begin{itemize}
  \item \rori~\code{rd, rs1, shamt}: rotation δεξιά κατά σταθερό αριθμό
    θέσεων (immediate). Ισοδύναμα, \code{rori rd, rs1, 64-k} εκτελεί
    rotation αριστερά κατά $k$ θέσεις.
  \item \insn{andn}~\code{rd, rs1, rs2}: AND-NOT ($\text{rs1} \wedge
    \overline{\text{rs2}}$). Υπολογίζει bit-clear σε μία εντολή.
  \item \insn{rev8}~\code{rd, rs1}: byte-reverse — αντιστρέφει τη σειρά
    των 8 bytes μιας 64-bit λέξης (endianness conversion).
  \item \insn{orc.b}~\code{rd, rs1}: OR-combine bytes — κάθε byte του
    αποτελέσματος γίνεται \code{0xFF} αν το αντίστοιχο byte εισόδου είναι
    μη μηδενικό, αλλιώς \code{0x00}.
\end{itemize}

\paragraph{Αντιστοίχιση σε Keccak.}
Η εσωτερική μετάθεση Keccak-f[1600] (βλ.~\cref{sec:keccak-theory}) απαιτεί
\num{25} lane rotations ανά γύρο (βήμα $\rho$) και \num{5} AND-NOT πράξεις
ανά σειρά (βήμα $\chi$). Χωρίς \gls{zbb}, κάθε 64-bit rotation απαιτεί δύο
εντολές shift και μία OR (\code{slli} + \code{srli} + \code{or} = 3 εντολές),
ενώ κάθε AND-NOT απαιτεί μία αντιστροφή και μία AND (\code{not} + \code{and}
= 2 εντολές). Με \gls{zbb}, η rotation εκτελείται σε μία \rori και η AND-NOT σε
μία \insn{andn} — μείωση \pct{67} και \pct{50} αντίστοιχα σε instruction
count ανά πράξη.

\paragraph{Μηχανισμός auto-lowering.}
Σε αντίθεση με τη \gls{zbc}, οι εντολές \gls{zbb} εκπέμπονται αυτόματα από τον
compiler χωρίς χρήση intrinsics. Ο μεταγλωττιστής αναγνωρίζει τα C idioms
\code{(x << k) | (x >> (64-k))} και \code{\textasciitilde{}b \& a} και τα
αντικαθιστά με \rori και \insn{andn} αντίστοιχα, αρκεί η επέκταση \gls{zbb} να
είναι ενεργή στο \code{-march} flag. Αυτός ο μηχανισμός
\defterm{auto-lowering} σημαίνει ότι ο πηγαίος κώδικας δεν χρειάζεται
τροποποίηση — η βελτιστοποίηση προκύπτει αποκλειστικά από τις compilation
flags. Τα ποσοτικά αποτελέσματα του auto-lowering αναλύονται
στην~\cref{sec:isa-ablation}.

\subsection{Η Επέκταση Zbkb: Bitmanip for Cryptography}
\label{ssec:zbkb-extension}

Η επέκταση Zbkb (Bit-manipulation for cryptography) αποτελεί υποσύνολο
εντολών σχεδιασμένων ειδικά για κρυπτογραφικές εφαρμογές. Στην πράξη, οι
εντολές που αξιοποιεί η παρούσα εργασία (\rori, \insn{andn}, \insn{rev8})
ανήκουν ταυτόχρονα στη \gls{zbb} και στη Zbkb — η Zbkb ορίστηκε ως ξεχωριστή
επέκταση για να επιτρέψει σε μικροελεγκτές που δεν υλοποιούν πλήρη \gls{zbb} να
παρέχουν τουλάχιστον τις κρυπτογραφικά κρίσιμες εντολές. Η εντολή
\insn{brev8} (bit-reverse εντός κάθε byte) ανήκει αποκλειστικά στη Zbkb και
χρησιμοποιείται σε αλγορίθμους που απαιτούν bit-reflection (π.χ.\ CRC,
GHASH), αλλά δεν αξιοποιείται στην παρούσα υλοποίηση \gls{hqc}.

Η \cref{tab:scalar-crypto-instructions} συνοψίζει τις εντολές ανά επέκταση
και την αντιστοίχισή τους σε κρυπτογραφικά primitives της παρούσας εργασίας.
Η αλληλοεπικάλυψη μεταξύ \gls{zbb} και Zbkb αντικατοπτρίζει τη σχεδιαστική
φιλοσοφία του RISC-V: οι ίδιες εντολές εξυπηρετούν τόσο γενικό bit-manipulation
όσο και κρυπτογραφικές ανάγκες, μεγιστοποιώντας την αξιοποίηση πυριτίου.

Οι scalar κρυπτογραφικές επεκτάσεις μετασχηματίζουν τους δύο κυρίαρχους
υπολογιστικούς πυρήνες του \gls{hqc} σε επίπεδο μεμονωμένων πράξεων: η \gls{zbc}
μειώνει το κόστος κάθε στοιχειώδους πολυωνυμικού γινομένου κατά \speedup{320},
ενώ η \gls{zbb} μειώνει το κόστος κάθε Keccak rotation και AND-NOT κατά
\speedup{3} και \speedup{2} αντίστοιχα. Η αξιοποίηση αυτών των εντολών στο
πλαίσιο ολόκληρου του αλγορίθμου — μέσω Karatsuba recursion, software
pipelining και compile-time code generation — παρουσιάζεται αναλυτικά στα
Κεφάλαια~\ref{ch:polymul-optimization} και~\ref{ch:kernel-optimization}.

\section{Αρχιτεκτονική Διανυσματικής Μονάδας (RVV 1.0)}
\label{sec:rvv-architecture}

Η διανυσματική επέκταση \gls{rvv} αποτελεί τον θεμελιώδη μηχανισμό
αξιοποίησης \gls{dlp} στην αρχιτεκτονική RISC-V. Τυποποιήθηκε στην
έκδοση~1.0 τον Νοέμβριο 2021~\cite{RISCV-vector-spec} και αποτελεί υποχρεωτική
επέκταση στο προφίλ RVA23 (βλ.~\cref{sec:extension-naming}). Η ενότητα αυτή
παρουσιάζει τη γενική αρχιτεκτονική, τους μηχανισμούς παραμετροποίησης, το
μοντέλο προγραμματισμού strip-mining, και τις κατηγορίες εντολών που
αξιοποιούνται στην παρούσα εργασία.

\subsection{Γενική Αρχιτεκτονική και Vector-Length Agnosticism}
\label{ssec:rvv-vla}

Η \gls{rvv} ορίζει \num{32} vector registers (\code{v0}–\code{v31}), κάθε
ένας πλάτους \VLEN~bits. Η παράμετρος \VLEN αποτελεί
\defterm{hardware parameter}: καθορίζεται κατά τον σχεδιασμό του
επεξεργαστή και παραμένει σταθερή κατά την εκτέλεση. Τυπικές τιμές
κυμαίνονται από \num{128}~bits (ελάχιστη συμβατή υλοποίηση) έως
\num{2048}~bits (υψηλής απόδοσης σχεδιασμοί), με τον περιορισμό ότι
$\VLEN = 2^k$ για κάποιο ακέραιο $k \geq 7$. Η \cref{fig:rvv-regfile}
απεικονίζει τη δομή του vector register file.

\begin{figure}[htbp]
  \centering
  \input{figures/ch3-riscv/rvv-register-file.tex}
  \caption{Δομή του vector register file στο \RVV: \num{32} καταχωρητές
    πλάτους \VLEN~bits. Η τιμή \VLEN είναι άγνωστη κατά τη μεταγλώττιση —
    ο κώδικας ανακαλύπτει το πλάτος κατά την εκτέλεση μέσω του \gls{csr}
    \code{vlenb}. Ο καταχωρητής \code{v0} χρησιμοποιείται ως mask register
    σε masked operations.}
  \label{fig:rvv-regfile}
\end{figure}

Η θεμελιώδης σχεδιαστική αρχή του \RVV είναι η \gls{vla} φιλοσοφία: ο
πηγαίος κώδικας δεν κωδικοποιεί καμία υπόθεση για την τιμή \VLEN. Ο ίδιος
binary εκτελείται σε οποιοδήποτε hardware \VLEN χωρίς recompilation — ο
μηχανισμός \insn{vsetvl} (βλ.~\cref{ssec:strip-mining}) ρυθμίζει δυναμικά
τον αριθμό στοιχείων ανά vector operation. Αυτή η αρχή διαφοροποιεί το \RVV
τόσο από τα σταθερού πλάτους SIMD μοντέλα (x86 SSE/AVX, ARM NEON) όσο και
από τα packed-SIMD μοντέλα παλαιότερων αρχιτεκτονικών. Η πρακτική συνέπεια
είναι ότι κώδικας γραμμένος σήμερα για \VLEN=256 θα αξιοποιήσει αυτόματα
μελλοντικό υλικό με \VLEN=512 ή \VLEN=1024 — η ανάλυση κλιμάκωσης ως προς
\VLEN παρουσιάζεται στο \cref{ch:results}.

\subsection{Control/Status Registers και Παραμετροποίηση}
\label{ssec:rvv-csrs}

Η συμπεριφορά κάθε vector operation καθορίζεται από τρεις \glspl{csr} που
ρυθμίζονται μέσω της εντολής \insn{vsetvli}/\insn{vsetvl}:

\begin{itemize}
  \item \code{vtype}: κωδικοποιεί τέσσερα πεδία — \gls{sew} (πλάτος
    στοιχείου: 8, 16, 32 ή 64~bits), \gls{lmul} (ομαδοποίηση
    καταχωρητών: $\frac{1}{8}$, $\frac{1}{4}$, $\frac{1}{2}$, 1, 2, 4, 8),
    \code{vta} (tail agnostic/undisturbed) και \code{vma} (mask
    agnostic/undisturbed). Το πεδίο \code{vill} σηματοδοτεί μη έγκυρο
    συνδυασμό.
  \item \code{vl}: το ενεργό μήκος διανύσματος (vector length) — ο αριθμός
    στοιχείων που επεξεργάζεται η τρέχουσα εντολή. Ρυθμίζεται αυτόματα
    από τη \insn{vsetvl} ως $\code{vl} = \min(\text{AVL}, \VLMAX)$, όπου
    AVL (Application Vector Length) είναι ο αριθμός στοιχείων που απομένουν
    προς επεξεργασία.
  \item \code{vlenb}: read-only \gls{csr} που επιστρέφει $\VLEN / 8$ σε
    bytes — ο μοναδικός τρόπος ανακάλυψης του hardware \VLEN κατά την
    εκτέλεση.
\end{itemize}

Η μέγιστη χωρητικότητα ενός vector register group υπολογίζεται από τον τύπο:
\begin{equation}
  \VLMAX = \frac{\VLEN}{\SEW} \times \LMUL.
  \label{eq:vlmax}
\end{equation}
Η \cref{tab:vlmax-combinations} παρουσιάζει τιμές \VLMAX για
αντιπροσωπευτικούς συνδυασμούς. Στην παρούσα εργασία, η κυρίαρχη
παραμετροποίηση είναι $\SEW = 64$, $\LMUL = 4$ (Karatsuba recomposition
και Zvbc leaf), η οποία παρέχει $\VLMAX = 16$ στοιχεία σε \VLEN=256.

  \centering
  \caption{Τιμές \VLMAX για αντιπροσωπευτικούς συνδυασμούς
    \VLEN/\SEW/\LMUL. Η γραμμή με \VLEN=256, \SEW=64, \LMUL=4
    αντιστοιχεί στην κυρίαρχη παραμετροποίηση της παρούσας εργασίας.}
  \label{tab:vlmax-combinations}
  \input{figures/ch3-riscv/rvv-vlmax-table.tex}

\paragraph{Παράδειγμα.}
Σε hardware με $\VLEN = 256$, η ρύθμιση $\SEW = 64$, $\LMUL = 1$ παρέχει
$\VLMAX = 256 / 64 \times 1 = 4$ στοιχεία ανά vector register. Αυξάνοντας
σε $\LMUL = 4$, τέσσερις διαδοχικοί καταχωρητές ομαδοποιούνται σε ένα
logical register group, παρέχοντας $\VLMAX = 16$ στοιχεία — αρκετά για να
καλύψουν ολόκληρο τον Karatsuba leaf ($n = 16$ λέξεις) σε μία vector
operation.

\subsection{Strip-Mining και ο Μηχανισμός vsetvl}
\label{ssec:strip-mining}

Η \gls{vla} φιλοσοφία υλοποιείται μέσω ενός θεμελιώδους μοτίβου
προγραμματισμού: του \defterm{strip-mining}. Ο μεταγλωττιστής δεν γνωρίζει
την τιμή \VLEN κατά τη μεταγλώττιση — κατά συνέπεια, δεν μπορεί να
υπολογίσει στατικά πόσα στοιχεία χωράνε σε ένα vector register. Ο βρόχος
strip-mining λύνει αυτό το πρόβλημα αντλώντας δυναμικά τόσα στοιχεία όσα
χωράνε ανά iteration (\cref{lst:strip-mining-pattern}):

\begin{lstlisting}[language=C, caption={Θεμελιώδες μοτίβο strip-mining σε
  \RVV. Η \code{vsetvl} επιστρέφει $\code{vl} = \min(n, \VLMAX)$ — ο
  βρόχος τερματίζει αυτόματα ανεξαρτήτως \VLEN.},
  label={lst:strip-mining-pattern}]
for (size_t n = total; n > 0; n -= vl) {
    size_t vl = __riscv_vsetvl_e64m4(n);
    /* vector operations on vl elements */
}
\end{lstlisting}

Η εντολή \insn{vsetvl} εκτελεί δύο λειτουργίες ταυτόχρονα: ρυθμίζει τον
\gls{csr} \code{vtype} (καθορίζοντας \SEW και \LMUL) και επιστρέφει στον
scalar register \code{rd} τον αριθμό στοιχείων που θα επεξεργαστεί η
επόμενη vector operation. Η τιμή αυτή ικανοποιεί πάντα
$\code{vl} \leq \VLMAX$ — στην τελευταία iteration, αν τα εναπομείναντα
στοιχεία είναι λιγότερα από \VLMAX, η \insn{vsetvl} επιστρέφει τον
ακριβή αριθμό τους. Αυτός ο μηχανισμός εγγυάται ορθότητα χωρίς
boundary checks ή padding.

Η \cref{fig:strip-mining-vis} απεικονίζει τη λειτουργία strip-mining σε
array \num{20} στοιχείων: σε hardware με $\VLMAX = 4$ απαιτούνται \num{5}
iterations, ενώ σε hardware με $\VLMAX = 8$ απαιτούνται μόνο \num{3}
iterations (η τελευταία με $\code{vl} = 4$). Ο κώδικας παραμένει ίδιος —
μόνο ο αριθμός iterations μεταβάλλεται.

\begin{figure}[htbp]
  \centering
  \input{figures/ch3-riscv/rvv-strip-mining.tex}
  \caption{Strip-mining ενός array \num{20} στοιχείων σε δύο hardware
    configurations. Πάνω: $\VLMAX = 4$ (5 iterations). Κάτω: $\VLMAX = 8$
    (3 iterations, τελευταία με $\code{vl} = 4$). Ο ίδιος κώδικας
    εκτελείται σε αμφότερα — η \insn{vsetvl} προσαρμόζει αυτόματα τον
    αριθμό στοιχείων ανά iteration.}
  \label{fig:strip-mining-vis}
\end{figure}

\paragraph{Πρακτικό παράδειγμα: VLA helper.}
Η ακόλουθη συνάρτηση αποτελεί πραγματικό κώδικα από την παρούσα υλοποίηση
— εκτελεί element-wise XOR δύο arrays 64-bit λέξεων χρησιμοποιώντας
strip-mining με $\SEW = 64$, $\LMUL = 4$ (\cref{lst:rvv-xor-helper}):

\begin{lstlisting}[language=C, caption={VLA helper \code{rvv\_xor\_u64} από
  τον Karatsuba recomposition πυρήνα. Η παραμετροποίηση $\LMUL = 4$
  παρέχει $\VLMAX = 16$ στοιχεία σε \VLEN=256.},
  label={lst:rvv-xor-helper}]
static inline void rvv_xor_u64(uint64_t *dst,
    const uint64_t *src1, const uint64_t *src2, size_t n_words)
{
    size_t n = n_words;
    while (n > 0) {
        size_t vl = __riscv_vsetvl_e64m4(n);
        vuint64m4_t v1 = __riscv_vle64_v_u64m4(src1, vl);
        vuint64m4_t v2 = __riscv_vle64_v_u64m4(src2, vl);
        __riscv_vse64_v_u64m4(dst,
            __riscv_vxor_vv_u64m4(v1, v2, vl), vl);
        src1 += vl; src2 += vl; dst += vl; n -= vl;
    }
}
\end{lstlisting}

Η συνάρτηση αυτή αντικαθιστά τον scalar 4$\times$-unrolled βρόχο στον
generated Karatsuba header, μειώνοντας τον αριθμό εντολών ανά στοιχείο
και ενεργοποιώντας κλιμάκωση ως προς \VLEN (βλ.~\cref{ch:results}).

\subsection{Tail/Mask Policies και Κατηγορίες Εντολών}
\label{ssec:rvv-policies-instructions}

\paragraph{Tail και Mask policies.}
Κάθε vector operation επεξεργάζεται \code{vl} στοιχεία — τα στοιχεία
πέραν της θέσης \code{vl} (tail elements) και τα στοιχεία με μηδενικό
mask bit (inactive elements) υπόκεινται σε δύο πολιτικές:
\begin{itemize}
  \item \defterm{Tail-agnostic} (\code{vta}): τα tail elements μπορούν να
    λάβουν οποιαδήποτε τιμή — η υλοποίηση δεν εγγυάται διατήρηση. Αυτό
    επιτρέπει στο hardware να αποφύγει δαπανηρές read-modify-write
    λειτουργίες στο vector register file.
  \item \defterm{Mask-agnostic} (\code{vma}): τα inactive elements (mask
    bit = 0) μπορούν επίσης να λάβουν οποιαδήποτε τιμή.
\end{itemize}
Η παρούσα εργασία χρησιμοποιεί αποκλειστικά tail-agnostic/mask-agnostic
πολιτικές, καθώς κανένας πυρήνας δεν εξαρτάται από τις τιμές tail ή
inactive elements — η ορθότητα εξασφαλίζεται μέσω του strip-mining μοτίβου
που επεξεργάζεται ακριβώς τα απαιτούμενα στοιχεία.

\paragraph{Ο καταχωρητής \code{v0} ως mask.}
Σε masked operations, ο καταχωρητής \code{v0} λειτουργεί ως mask register:
κάθε bit $i$ του \code{v0} καθορίζει αν το στοιχείο $i$ θα επεξεργαστεί
(bit = 1) ή θα παραμείνει ανεπηρέαστο (bit = 0). Η παρούσα εργασία
αξιοποιεί masked operations στον constant-time sampling πυρήνα
(βλ.~\cref{sec:polymul-scalar}), όπου η εντολή \insn{vmseq} παράγει mask
και η \insn{vcpop} μετράει τα ενεργά bits.

\paragraph{LMUL register grouping.}
Ο μηχανισμός \gls{lmul} επιτρέπει την ομαδοποίηση διαδοχικών vector
registers σε ένα logical register group. Σε $\LMUL = 4$, οι καταχωρητές
\code{v0}–\code{v3} αποτελούν μία ομάδα, οι \code{v4}–\code{v7} μία
δεύτερη, κ.ο.κ. — συνολικά \num{8} ανεξάρτητες ομάδες αντί \num{32}
μεμονωμένων καταχωρητών. Η \cref{fig:lmul-grouping} απεικονίζει τη
διαφορά. Η αύξηση \LMUL αυξάνει τον αριθμό στοιχείων ανά vector operation
(μεγαλύτερο \VLMAX) αλλά μειώνει τον αριθμό διαθέσιμων ανεξάρτητων
τελεστέων — ένα trade-off μεταξύ throughput ανά εντολή και register
pressure.

\begin{figure}[htbp]
  \centering
  \input{figures/ch3-riscv/rvv-lmul-grouping.tex}
  \caption{Ομαδοποίηση vector registers μέσω \LMUL. Αριστερά: $\LMUL = 1$
    (\num{32} ανεξάρτητοι καταχωρητές, $\VLMAX = \VLEN/\SEW$). Δεξιά:
    $\LMUL = 4$ (\num{8} ομάδες, $\VLMAX = 4 \times \VLEN/\SEW$).
    Η αύξηση \LMUL αυξάνει τα στοιχεία ανά εντολή αλλά μειώνει τους
    διαθέσιμους ανεξάρτητους τελεστέους.}
  \label{fig:lmul-grouping}
\end{figure}

Στην παρούσα εργασία, η επιλογή \LMUL καθορίζεται από τις ανάγκες κάθε
πυρήνα: ο Karatsuba recomposition χρησιμοποιεί $\LMUL = 4$ (ισορροπία
μεταξύ throughput και register availability για τα ενδιάμεσα αποτελέσματα),
ενώ ο Keccak χρησιμοποιεί $\LMUL = 8$ (ολόκληρο το 25-lane state χωράει
σε μία ομάδα σε $\VLEN \geq 256$). Η \code{memcpy} χρησιμοποιεί επίσης
$\LMUL = 8$ για μεγιστοποίηση bandwidth.

\subsection{Motivating Example: XOR Loop σε RVV}
\label{ssec:rvv-xor-example}

Η πρακτική εφαρμογή των μηχανισμών strip-mining, \insn{vsetvl} και VLA
αποσαφηνίζεται μέσω ενός πλήρους worked example: η συνάρτηση
\code{vect\_add} εκτελεί element-wise XOR δύο πολυωνυμικών vectors —
θεμελιώδης πράξη στο \gls{hqc} (πρόσθεση πολυωνύμων σε $\GFpoly$). Η
\cref{fig:rvv-xor-comparison} παρουσιάζει τη σύγκριση μεταξύ scalar C
και \RVV intrinsics.

\begin{figure}[htbp]
  \centering
  \input{figures/ch3-riscv/rvv-xor-example.tex}
  \caption{Σύγκριση scalar C loop (αριστερά) και \RVV intrinsics (δεξιά)
    για element-wise XOR δύο arrays. Ο \RVV κώδικας χρησιμοποιεί
    strip-mining: η \code{vsetvl} ρυθμίζει δυναμικά τον αριθμό στοιχείων,
    η \code{vle64} φορτώνει, η \code{vxor} υπολογίζει, και η \code{vse64}
    αποθηκεύει — ο βρόχος τερματίζει αυτόματα ανεξαρτήτως \VLEN.}
  \label{fig:rvv-xor-comparison}
\end{figure}

Η scalar υλοποίηση εκτελεί \num{3} εντολές ανά στοιχείο (load, XOR,
store) σε \code{size} iterations. Η \RVV υλοποίηση εκτελεί \num{5}
εντολές ανά iteration (\insn{vsetvli} + \insn{vle64} $\times 2$ +
\insn{vxor} + \insn{vse64}), αλλά κάθε iteration επεξεργάζεται \VLMAX
στοιχεία. Σε $\VLEN = 256$, $\LMUL = 8$: $\VLMAX = 32$ στοιχεία ανά
iteration, δηλαδή $5 / 32 \approx 0.16$ εντολές ανά στοιχείο — μείωση
\speedup{19} σε instruction count. Η πραγματική μείωση εξαρτάται από τον
αριθμό στοιχείων (overhead \insn{vsetvli} αμελητέο για μεγάλα arrays) και
τη ρύθμιση \LMUL.

Η συνάρτηση \code{vect\_add} αποτελεί χαρακτηριστικό παράδειγμα
auto-vectorization candidate: ο scalar βρόχος είναι αρκετά απλός ώστε ο
compiler να τον vectorize αυτόματα (βλ.~\cref{sec:isa-ablation}). Ωστόσο,
η ρητή χρήση intrinsics εγγυάται τη σωστή παραμετροποίηση \LMUL και
εξαλείφει την εξάρτηση από τις ευρετικές αποφάσεις του compiler — κρίσιμο
σε performance-sensitive πυρήνες όπου η επιλογή \LMUL επηρεάζει άμεσα τον
αριθμό iterations.

\paragraph{Σύνδεση με τη βελτιστοποίηση.}
Η ίδια δομή strip-mining εφαρμόζεται σε ολόκληρη τη vectorized υλοποίηση:
στους Karatsuba recomposition helpers (\code{rvv\_copy\_u64},
\code{rvv\_xor3\_u64}), στον Zvbc leaf kernel (\code{vclmul\_leaf}), στον
Keccak permutation, και στη vectorized \code{memcpy}. Η ομοιομορφία του
μοτίβου σημαίνει ότι η κλιμάκωση ως προς \VLEN επηρεάζει ομοιόμορφα
όλους τους πυρήνες — με εξαίρεση εκείνους που λειτουργούν σε σταθερό
μέγεθος δεδομένων (βλ.~\cref{ch:results} για ποσοτική ανάλυση).

\section{Διανυσματικές Κρυπτογραφικές Επεκτάσεις (\Zvbc, \Zvbb)}
\label{sec:vector-crypto-extensions}

Οι διανυσματικές κρυπτογραφικές επεκτάσεις \gls{zvbc} και \gls{zvbb} αποτελούν τη
φυσική προέκταση των scalar επεκτάσεων \gls{zbc} και \gls{zbb}
(βλ.~\cref{sec:scalar-extensions}) στο vector domain. Τυποποιήθηκαν τον
Σεπτέμβριο 2023 ως μέρος του Volume~II (Vector Cryptography) της
προδιαγραφής RISC-V Cryptography Extensions~\cite{RISCV-crypto-spec} και
αποτελούν τη βάση του Tier~3 profile της παρούσας εργασίας.
Η ενότητα αυτή παρουσιάζει τη σημασιολογία κάθε εντολής, την αντιστοίχισή
της σε κρυπτογραφικά primitives, και τον λόγο που αυτές οι εντολές δεν
εκπέμπονται αυτόματα από τον compiler.

\subsection{Η Επέκταση \Zvbc: Vector Carry-Less Multiplication}
\label{ssec:zvbc-extension}

Η επέκταση \gls{zvbc} ορίζει δύο εντολές που εκτελούν carry-less multiplication
σε κάθε στοιχείο ενός vector register ανεξάρτητα:

\begin{itemize}
  \item \vclmul~\code{vd, vs2, vs1}: υπολογίζει τα κάτω 64~bit του
    carry-less γινομένου κάθε ζεύγους στοιχείων
    $\text{vs2}[i] \polymul \text{vs1}[i]$, για $i = 0, \ldots, \code{vl}-1$.
  \item \vclmulh~\code{vd, vs2, vs1}: υπολογίζει τα άνω 64~bit του
    ίδιου γινομένου ανά στοιχείο.
\end{itemize}

Η σημασιολογία είναι ταυτόσημη με τις scalar \clmul/\clmulh
(βλ.~\cref{eq:clmul-definition}), εφαρμοζόμενη παράλληλα σε \code{vl}
ζεύγη στοιχείων. Σε $\SEW = 64$, $\LMUL = 4$, $\VLEN = 256$: κάθε
εντολή \vclmul επεξεργάζεται $\VLMAX = 16$ ανεξάρτητα 64-bit carry-less
γινόμενα ταυτόχρονα. Η πράξη αυτή αντιστοιχεί ακριβώς στα leaf products
του Karatsuba πολυωνυμικού πολλαπλασιασμού — κάθε leaf υπολογίζει $n$
ζεύγη $a[i] \polymul b[j]$ τα οποία μπορούν να εκτελεστούν παράλληλα
χωρίς εξαρτήσεις δεδομένων.

\paragraph{Μοτίβο χρήσης: splat-and-sweep.}
Στην παρούσα υλοποίηση, ο vectorized Karatsuba leaf χρησιμοποιεί το μοτίβο
\defterm{splat-and-sweep}: ένα scalar στοιχείο $a[i]$ αντιγράφεται σε
όλα τα lanes ενός vector register μέσω \insn{vmv.v.x} (splat), και
στη συνέχεια πολλαπλασιάζεται carry-less με ολόκληρο τον vector $b[j \ldots
j + \code{vl} - 1]$ μέσω ενός ζεύγους \vclmul/\vclmulh (sweep). Αυτό
αντικαθιστά \code{vl} ζεύγη scalar \clmul/\clmulh με \num{3} vector
εντολές (\insn{vmv.v.x} + \vclmul + \vclmulh), μειώνοντας τον αριθμό
δυναμικών εντολών κατά παράγοντα $\sim\!\VLMAX / 3$.

\paragraph{Περιορισμός \SEW.}
Η \gls{zvbc} υποστηρίζει αποκλειστικά $\SEW = 64$ — δεν ορίζονται εκδόσεις
για μικρότερα πλάτη στοιχείων. Αυτός ο περιορισμός αντικατοπτρίζει τη
σχεδιαστική απόφαση ότι carry-less multiplication σε μικρότερα πλάτη
(8, 16, 32~bit) μπορεί να εξυπηρετηθεί μέσω widening ή narrowing
operations πάνω στα 64-bit αποτελέσματα. Στην παρούσα εργασία, ο
περιορισμός δεν αποτελεί εμπόδιο: τόσο ο πολυωνυμικός πολλαπλασιασμός
σε $\GF{2}[x]/(x^N - 1)$ όσο και η αριθμητική $\GF{2^8}$ λειτουργούν
σε 64-bit λέξεις.

\subsection{Η Επέκταση \Zvbb: Vector Bit-Manipulation}
\label{ssec:zvbb-extension}

Η επέκταση \gls{zvbb} παρέχει vector εκδόσεις εντολών bit-manipulation
σχεδιασμένων για κρυπτογραφικές εφαρμογές:

\begin{itemize}
  \item \insn{vror.vv}~\code{vd, vs2, vs1}: rotation δεξιά κάθε
    στοιχείου κατά μεταβλητό αριθμό θέσεων (ανά lane, από τον \code{vs1}).
  \item \insn{vror.vi}~\code{vd, vs2, imm}: rotation δεξιά κάθε
    στοιχείου κατά σταθερό αριθμό θέσεων (6-bit immediate).
  \item \insn{vandn.vv}~\code{vd, vs2, vs1}: AND-NOT ανά στοιχείο
    ($\text{vs2}[i] \wedge \overline{\text{vs1}[i]}$).
  \item \insn{vbrev8.v}~\code{vd, vs2}: bit-reverse εντός κάθε byte
    κάθε στοιχείου.
\end{itemize}

\paragraph{Αντιστοίχιση σε Keccak.}
Η εσωτερική μετάθεση Keccak-f[1600] (βλ.~\cref{sec:keccak-theory})
αποτελεί τον κύριο beneficiary της \gls{zvbb} στην παρούσα εργασία. Το βήμα
$\rho$ (lane rotation) απαιτεί \num{25} rotations ανά γύρο με
διαφορετικό offset ανά lane — η \insn{vror.vv} εκτελεί όλες τις
rotations ενός vector register σε μία εντολή, χρησιμοποιώντας ένα
δεύτερο vector register ως πίνακα offsets. Το βήμα $\chi$ (μη γραμμικό
βήμα) απαιτεί \num{5} AND-NOT πράξεις ανά σειρά — η \insn{vandn.vv}
εκτελεί κάθε μία σε μία εντολή αντί δύο (inversion + AND).

Στη vectorized υλοποίηση Keccak (LMUL=8, $\VLEN \geq 256$), ολόκληρο
το 25-lane state φορτώνεται σε ένα vector register group. Τα βήματα
$\rho$ και $\pi$ εκτελούνται μέσω ενός ζεύγους \insn{vrgather.vv}
(permutation) + \insn{vror.vv} (rotation), ενώ το βήμα $\chi$ εκτελείται
μέσω δύο \insn{vrgather.vv} (ανάκτηση $A[x+1]$ και $A[x+2]$) +
\insn{vandn.vv} + \insn{vxor.vv}. Χωρίς \gls{zvbb}, κάθε rotation θα
απαιτούσε τρεις εντολές (\insn{vsll} + \insn{vsrl} + \insn{vor}) και
κάθε AND-NOT δύο (\insn{vnot} + \insn{vand}) — αύξηση \pct{200} και
\pct{100} αντίστοιχα σε instruction count ανά πράξη.

\paragraph{Η \insn{vror.vi} και compile-time immediates.}
Η μορφή \insn{vror.vi} (immediate rotation) αποτελεί ιδιαίτερα σημαντική
βελτιστοποίηση για τον Keccak: τα rotation offsets του βήματος $\rho$
είναι σταθερές γνωστές κατά τη μεταγλώττιση (0, 1, 62, 28, 27, 36, 44,
\ldots). Στη 2-way SoA (Structure-of-Arrays) υλοποίηση, κάθε lane
αποθηκεύεται σε ξεχωριστό vector register ($\LMUL = 1$, \code{vl} = 2
streams), και η rotation εκτελείται μέσω \insn{vror.vx} με scalar
immediate — ο compiler εκπέμπει \insn{vror.vi} για offsets $\leq 31$
και \insn{li} + \insn{vror.vx} για offsets $32$–$63$. Αυτό εξαλείφει
πλήρως τις memory loads για τον πίνακα rotation offsets.

\subsection{Αδυναμία Αυτόματης Εκπομπής από τον Compiler}
\label{ssec:zvbc-no-autoemit}

Σε αντίθεση με τις scalar εντολές \gls{zbb} (βλ.~\cref{ssec:zbb-extension}),
οι εντολές \gls{zvbc} και \gls{zvbb} δεν εκπέμπονται αυτόματα από τον compiler
μέσω pattern recognition. Η αιτία είναι δομική: ο compiler αναγνωρίζει
scalar idioms (\eg \code{(x << k) | (x >> (64-k))} $\to$ \rori) επειδή
αυτά αντιστοιχούν σε μεμονωμένες C εκφράσεις με σαφή σημασιολογία. Οι
αντίστοιχες vector πράξεις, ωστόσο, δεν εκφράζονται ως απλά C idioms —
ένας carry-less πολλαπλασιασμός σε $\GFpoly$ δεν αντιστοιχεί σε κανένα
standard C operator, και η vector rotation πολλαπλών lanes με
διαφορετικά offsets δεν αναγνωρίζεται από τα υπάρχοντα vectorization
passes.

\paragraph{Τεχνικοί λόγοι.}
Τρεις παράγοντες εμποδίζουν το auto-vectorization:
\begin{enumerate}
  \item \textbf{Απουσία scalar αντιστοίχου σε standard C:} η πράξη
    carry-less multiply δεν αντιστοιχεί σε κανέναν C operator (\code{*},
    \code{\^{}}, \code{\&}) — ο compiler δεν μπορεί να αναγνωρίσει ένα
    pattern που δεν υπάρχει στη γλώσσα.
  \item \textbf{Μη τετριμμένη vectorization:} ακόμη και αν ο scalar
    βρόχος χρησιμοποιεί \code{\_\_riscv\_clmul\_64()} intrinsics, ο
    auto-vectorizer δεν γνωρίζει ότι η scalar \clmul αντιστοιχεί στη
    vector \vclmul — δεν υπάρχει mapping στο compiler backend μεταξύ
    scalar crypto intrinsics και vector crypto εντολών.
  \item \textbf{Σύνθετα access patterns:} ο Karatsuba leaf δεν είναι
    απλός element-wise βρόχος — κάθε $a[i]$ πολλαπλασιάζεται με
    ολόκληρο τον vector $b[0 \ldots n-1]$ (splat-and-sweep), ένα
    μοτίβο που δεν ταιριάζει στα standard vectorization templates
    (unit-stride, strided, gather/scatter).
\end{enumerate}

Κατά συνέπεια, η αξιοποίηση \gls{zvbc} και \gls{zvbb} απαιτεί ρητή χρήση C
intrinsics: \code{\_\_riscv\_vclmul\_vv\_u64m4()},
\code{\_\_riscv\_vclmulh\_vv\_u64m4()}, \code{\_\_riscv\_vror\_vv\_u64m8()},
\code{\_\_riscv\_vandn\_vv\_u64m8()}. Τα intrinsics αυτά ορίζονται στο
header \code{<riscv\_vector.h>} και συμμετέχουν πλήρως στο optimization
pipeline (register allocation, scheduling), αλλά η επιλογή χρήσης τους
παραμένει αποκλειστικά στον προγραμματιστή. Η ποσοτική επίπτωση αυτού
του περιορισμού — δηλαδή η διαφορά μεταξύ compiler auto-vectorization
(Tier~2 χωρίς Zvbc) και ρητής χρήσης intrinsics (Tier~3 με Zvbc) —
αναλύεται στην~\cref{sec:isa-ablation}.

\paragraph{Σύνοψη αρχιτεκτονικής συνεισφοράς.}
Οι επεκτάσεις \gls{zvbc} και \gls{zvbb} μετασχηματίζουν τους δύο κυρίαρχους
υπολογιστικούς πυρήνες του \gls{hqc} στο vector domain: η \gls{zvbc} παρέχει
$\VLMAX$-fold παραλληλισμό στον carry-less πολλαπλασιασμό (Karatsuba
leaf), ενώ η \gls{zvbb} μειώνει κατά \speedup{3} τις εντολές rotation και
κατά \speedup{2} τις εντολές AND-NOT στον Keccak. Σε συνδυασμό με τη
\gls{vla} φιλοσοφία του \RVV, η απόδοση κλιμακώνεται αυτόματα με το
hardware \VLEN — χωρίς τροποποίηση πηγαίου κώδικα. Η αναλυτική
παρουσίαση της αξιοποίησης αυτών των εντολών στους βελτιστοποιημένους
πυρήνες ακολουθεί στα
Κεφάλαια~\ref{ch:polymul-optimization} και~\ref{ch:kernel-optimization}.

Η αξιοποίηση των κρυπτογραφικών επεκτάσεων που παρουσιάστηκαν στις
προηγούμενες ενότητες απαιτεί κατάλληλη μέθοδο παραγωγής κώδικα. Η
αρχιτεκτονική RISC-V παρέχει τέσσερις διακριτές μεθόδους, ταξινομημένες
κατά φθίνοντα βαθμό ελέγχου του προγραμματιστή επί του παραγόμενου κώδικα
μηχανής. Η ενότητα αυτή παρουσιάζει κάθε μέθοδο σε γενικό πλαίσιο —
ανεξάρτητα εφαρμογής — ενώ η συγκεκριμένη αντιστοίχιση στους πυρήνες της
παρούσας εργασίας τεκμηριώνεται στην~\cref{sec:methods-application}.

Η \cref{fig:programming-spectrum} απεικονίζει το φάσμα αφαίρεσης: στο

ο μεταγλωττιστής αναλαμβάνει αυτόνομα την εκπομπή εξειδικευμένων εντολών.
Κάθε μετακίνηση προς τα δεξιά αυξάνει τη δυνατότητα βελτιστοποίησης από
τον compiler αλλά μειώνει τον άμεσο έλεγχο επί του instruction scheduling
και register allocation.

\subsection{Καθαρή Assembly (\texttt{.S} αρχεία)}
\label{ssec:pure-assembly}

Η πρώτη μέθοδος παρέχει πλήρη χειροκίνητο έλεγχο σε κάθε πτυχή του
παραγόμενου κώδικα: register allocation, instruction ordering, memory
layout, και ακριβή encoding κάθε εντολής. Ο μεταγλωττιστής δεν παρεμβαίνει
— ο κώδικας assembly μεταφράζεται απευθείας σε κώδικα μηχανής χωρίς
βελτιστοποίηση, αναδιάταξη ή εξάλειψη εντολών.

\paragraph{Ευθύνες του προγραμματιστή.}
Η απουσία compiler intervention μεταφέρει ολόκληρο το βάρος ορθότητας στον
προγραμματιστή. Η συμμόρφωση με το RISC-V calling convention (ABI) πρέπει
να εξασφαλιστεί χειροκίνητα: σωστή χρήση caller-saved (\code{t0}–\code{t6},
\code{a0}–\code{a7}) και callee-saved (\code{s0}–\code{s11}) καταχωρητών,
ευθυγράμμιση stack pointer σε 16-byte boundary, και σωστή τοποθέτηση
ορισμάτων/επιστρεφόμενων τιμών. Σφάλματα σε αυτά τα σημεία δεν ανιχνεύονται
κατά τη μεταγλώττιση — εκδηλώνονται ως silent corruption κατά την εκτέλεση.

\paragraph{Τυπικές χρήσεις.}
Η καθαρή assembly χρησιμοποιείται αποκλειστικά σε περιπτώσεις όπου δεν
υπάρχει εναλλακτική: boot code (αρχικοποίηση stack pointer πριν τη δημιουργία
C runtime), interrupt handlers (ακριβής context save/restore), και ρουτίνες
που απαιτούν εντολές μη προσβάσιμες από C (\insn{ecall}, \insn{mret},
χειρισμός \glspl{csr} πριν την ενεργοποίηση C environment). Ο ακόλουθος
κώδικας αποτελεί χαρακτηριστικό παράδειγμα — ενεργοποίηση της διανυσματικής
μονάδας μέσω χειρισμού του \code{mstatus} \gls{csr} (\cref{lst:vector-enable}):

\begin{lstlisting}[language={[RISC-V]Assembler},
  caption={Ενεργοποίηση Vector Unit μέσω \code{mstatus.VS} σε bare-metal
    boot sequence. Η εντολή \insn{csrs} θέτει τα bits 10:9 (VS field) σε
    \q{Dirty} (11), σηματοδοτώντας στο hardware ότι η vector μονάδα είναι
    ενεργή. Η \insn{vsetvli} αρχικοποιεί τον \code{vtype} \gls{csr}.},
  label={lst:vector-enable}]
    li   t0, 0x600          /* mstatus.VS = Dirty (bits 10:9 = 11) */
    csrs mstatus, t0        /* Set VS field */
    vsetvli t0, zero, e64, m1, ta, ma  /* Init vtype CSR */
\end{lstlisting}

Η εντολή \insn{csrs} (CSR Set) εκτελεί bitwise OR μεταξύ του τρέχοντος
\code{mstatus} και της τιμής \code{0x600}, θέτοντας τα bits 10:9 χωρίς να
επηρεάζει τα υπόλοιπα πεδία. Αυτή η λειτουργία δεν εκφράζεται σε C χωρίς
inline assembly — αποτελεί privileged operation που απαιτεί M-mode πρόσβαση.

\subsection{Inline Assembly (\texttt{\_\_asm\_\_} / \texttt{\_\_asm\_\_ volatile})}
\label{ssec:inline-assembly}

Η δεύτερη μέθοδος ενσωματώνει μεμονωμένες εντολές assembly μέσα σε
συναρτήσεις C. Ο μεταγλωττιστής αντιμετωπίζει τα \code{volatile} blocks
ως \defterm{αδιαφανή} (opaque): δεν μπορεί να αναδιατάξει, εξαλείψει ή
βελτιστοποιήσει γύρω τους. Η σύνδεση μεταξύ assembly εντολών και C
μεταβλητών γίνεται μέσω ενός συστήματος \defterm{constraints} που
καθορίζει ποιοι καταχωρητές χρησιμοποιούνται ως είσοδοι και έξοδοι.

\paragraph{Σύνταξη constraints.}
Η γενική μορφή ενός inline assembly block είναι:
\begin{lstlisting}[language=C, numbers=none]
__asm__ volatile ("insn %0, %1, %2"
    : "=r"(output)       /* output operand */
    : "r"(input1), "r"(input2)  /* input operands */
    : /* clobbers */
);
\end{lstlisting}
Ο constraint \code{"=r"} δηλώνει ότι ο compiler πρέπει να εκχωρήσει έναν
\gls{gpr} για την έξοδο. Ο constraint \code{"=\&r"} (early-clobber)
δηλώνει ότι η έξοδος γράφεται πριν διαβαστούν όλες οι είσοδοι — ο compiler
πρέπει να εκχωρήσει διαφορετικό καταχωρητή από τις εισόδους. Η παράλειψη
early-clobber σε περιπτώσεις που απαιτείται αποτελεί συχνή πηγή silent
corruption: ο compiler μπορεί να τοποθετήσει είσοδο και έξοδο στον ίδιο
καταχωρητή, με αποτέλεσμα η εγγραφή εξόδου να καταστρέψει μια είσοδο που
δεν έχει ακόμη αναγνωστεί.

\paragraph{Χρήση: CSR reads.}
Η κύρια χρήση inline assembly στην παρούσα εργασία αφορά την ανάγνωση
\glspl{csr} μέτρησης απόδοσης, για τις οποίες δεν υπάρχει C intrinsic (\cref{lst:csr-read}):

\begin{lstlisting}[language=C,
  caption={Ανάγνωση \code{mcycle} (CSR 0xb00) μέσω inline assembly. Η
    δήλωση \code{volatile} εμποδίζει τον compiler να εξαλείψει ή
    αναδιατάξει την ανάγνωση — κρίσιμο για ακρίβεια μετρήσεων.},
  label={lst:csr-read}]
uint64_t hqc_rdcycle(void) {
    uint64_t cycles;
    __asm__ volatile ("csrr %0, 0xb00" : "=r"(cycles));
    return cycles;
}
\end{lstlisting}

Η δήλωση \code{volatile} είναι κρίσιμη: χωρίς αυτήν, ο compiler θα
μπορούσε να εξαλείψει την ανάγνωση ως dead code (αν η τιμή δεν
χρησιμοποιείται αμέσως) ή να τη μετακινήσει εκτός του μετρούμενου
τμήματος κώδικα. Η εντολή \insn{csrr} (CSR Read) αποτελεί ψευδοεντολή
για \code{csrrs rd, csr, x0} — αναγιγνώσκει τον \gls{csr} χωρίς να
τροποποιεί τα bits του.

\paragraph{Περιορισμοί.}
Η inline assembly παρουσιάζει δύο θεμελιώδεις αδυναμίες. Η πρώτη αφορά
την αδιαφάνεια: ο compiler δεν μπορεί να εφαρμόσει common subexpression
elimination (CSE), dead code elimination (DCE) ή instruction scheduling
στον κώδικα εντός του block — ακόμη και αν δύο διαδοχικά blocks υπολογίζουν
το ίδιο αποτέλεσμα, ο compiler δεν μπορεί να εξαλείψει τον πλεονασμό. Η
δεύτερη αφορά τη φορητότητα: η σύνταξη constraints είναι compiler-specific
(GCC/Clang) και η ορθότητα εξαρτάται από λεπτομέρειες υλοποίησης που
μπορεί να αλλάξουν μεταξύ εκδόσεων.

\subsection{C Intrinsics (\texttt{\_\_riscv\_*})}
\label{ssec:c-intrinsics}

Η τρίτη μέθοδος παρέχει συναρτήσεις μεταγλωττιστή (compiler builtins) που
αντιστοιχούν 1:1 σε εντολές μηχανής αλλά συμμετέχουν πλήρως στο
optimization pipeline. Σε αντίθεση με την inline assembly, τα intrinsics
είναι πλήρως ορατά στον compiler: υπόκεινται σε register allocation,
instruction scheduling, common subexpression elimination, constant folding
και dead code elimination.

\paragraph{Διαθέσιμα headers.}
Τα RISC-V intrinsics παρέχονται μέσω δύο standard headers:
\begin{itemize}
  \item \code{<riscv\_bitmanip.h>}: scalar intrinsics για \gls{zbc}, \gls{zbb} και
    Zbs — \eg \code{\_\_riscv\_clmul\_64(a, b)},
    \code{\_\_riscv\_clmulh\_64(a, b)}, \code{\_\_riscv\_ror\_64(x, k)}.
  \item \code{<riscv\_vector.h>}: vector intrinsics για \RVV 1.0, \gls{zvbc}
    και \gls{zvbb} — \eg \code{\_\_riscv\_vclmul\_vv\_u64m4(vs2, vs1, vl)},
    \code{\_\_riscv\_vror\_vv\_u64m8(vs2, vs1, vl)},
    \code{\_\_riscv\_vsetvl\_e64m4(avl)}.
\end{itemize}

\paragraph{Πλεονεκτήματα έναντι inline assembly.}
Τρία χαρακτηριστικά καθιστούν τα intrinsics ανώτερα της inline assembly
για κρυπτογραφικούς πυρήνες. Η \defterm{type safety} εξασφαλίζει ότι
σφάλματα τύπου (\eg πέρασμα \code{vuint64m4\_t} σε θέση
\code{vuint64m8\_t}) ανιχνεύονται κατά τη μεταγλώττιση — αντί να
εκδηλωθούν ως silent corruption κατά την εκτέλεση. Η \defterm{πλήρης
ορατότητα στον optimizer} επιτρέπει στον compiler να εξαλείψει
πλεονάζοντες υπολογισμούς, να αναδιατάξει εντολές για βέλτιστο pipeline
utilization, και να εκχωρήσει καταχωρητές βάσει global register pressure
analysis. Η \defterm{φορητότητα μεταξύ compiler versions} εξασφαλίζεται
από τον τυποποιημένο ορισμό κάθε intrinsic — σε αντίθεση με τη σύνταξη
constraints που μπορεί να διαφέρει μεταξύ GCC και Clang.

Η \cref{fig:inline-vs-intrinsic} παρουσιάζει τη σύγκριση για τον ίδιο
υπολογισμό (scalar carry-less multiply): η inline assembly απαιτεί
\num{5} γραμμές constraint syntax και παράγει αδιαφανές block, ενώ το
intrinsic απαιτεί \num{1} γραμμή και παραμένει πλήρως βελτιστοποιήσιμο.

\begin{figure}[htbp]
  \centering
  \input{figures/ch3-riscv/inline-asm-vs-intrinsic.tex}
  \caption{Σύγκριση inline assembly (αριστερά) και C intrinsic (δεξιά) για
    scalar carry-less multiplication. Αμφότερα παράγουν την ίδια εντολή
    \clmul, αλλά το intrinsic παρέχει type safety, πλήρη ορατότητα στον
    optimizer, και μονογραμμική σύνταξη.}
  \label{fig:inline-vs-intrinsic}
\end{figure}

\paragraph{Περιορισμός: μη πλήρης κάλυψη ISA.}
Δεν υπάρχουν intrinsics για κάθε εντολή RISC-V. Εντολές που αφορούν
privileged operations (\insn{csrr}, \insn{csrw}, \insn{mret}), control
flow (\insn{ecall}, \insn{wfi}) ή ειδικές λειτουργίες hardware
(\insn{fence.i}) δεν καλύπτονται — για αυτές απαιτείται inline assembly.
Ωστόσο, το σύνολο των κρυπτογραφικών εντολών (\gls{zbc}, \gls{zbb}, \gls{zvbc}, \gls{zvbb})
καλύπτεται πλήρως από intrinsics, καθιστώντας την inline assembly περιττή
για τους υπολογιστικούς πυρήνες.

\subsection{Απλός C με Compiler Auto-Lowering}
\label{ssec:auto-lowering}

Η τέταρτη μέθοδος δεν απαιτεί καμία ρητή παρέμβαση του προγραμματιστή:
ο μεταγλωττιστής αναγνωρίζει αυτόματα C idioms και εκπέμπει εξειδικευμένες
εντολές, αρκεί η αντίστοιχη extension να είναι ενεργή στο \code{-march}
flag. Ο πηγαίος κώδικας παραμένει αμετάβλητος — η βελτιστοποίηση προκύπτει
αποκλειστικά από τη ρύθμιση μεταγλώττισης.

\paragraph{Αναγνωριζόμενα patterns.}
Ο compiler αναγνωρίζει τα ακόλουθα C idioms και τα αντικαθιστά με
μονολεκτικές εντολές:
\begin{itemize}
  \item \code{\textasciitilde{}a \& b} $\to$ \insn{andn} (\gls{zbb}): η
    αντιστροφή και η σύζευξη συγχωνεύονται σε μία εντολή.
  \item \code{(x << n) | (x >> (64-n))} $\to$ \rori (\gls{zbb}): το
    rotation idiom αναγνωρίζεται ανεξαρτήτως σειράς shift/OR.
  \item \code{base + idx*8} $\to$ \insn{sh3add} (Zba): η πράξη
    address scaling (\code{slli 3} + \code{add}) συγχωνεύεται σε μία
    εντολή address generation.
  \item \code{x |= (1ULL << pos)} $\to$ \insn{bset} (Zbs): η πράξη
    single-bit set αντικαθίσταται από μία εντολή.
\end{itemize}

\paragraph{Πλεονέκτημα: μηδενική αλλαγή πηγαίου κώδικα.}
Η μέθοδος auto-lowering παρέχει βελτιστοποίηση χωρίς κόστος συντήρησης:
ο ίδιος πηγαίος κώδικας μεταγλωττίζεται σε διαφορετικές εντολές ανάλογα
με τις ενεργές extensions. Σε target χωρίς \gls{zbb}, η έκφραση
\code{(x << 3) | (x >> 61)} μεταγλωττίζεται σε τρεις εντολές
(\insn{slli} + \insn{srli} + \insn{or}). Σε target με \gls{zbb}, η ίδια
έκφραση μεταγλωττίζεται σε μία \insn{rori rd, rs, 61}. Η αλλαγή
απαιτεί μόνο τροποποίηση του \code{-march} flag — ο πηγαίος κώδικας
παραμένει ίδιος.

\paragraph{Περιορισμός: μη αναγνώριση σύνθετων patterns.}
Ο μηχανισμός auto-lowering αποτυγχάνει σε σύνθετα κρυπτογραφικά patterns.
Ο compiler δεν αναγνωρίζει ότι ένας βρόχος carry-less multiplication
αντιστοιχεί στην εντολή \clmul — η πράξη δεν εκφράζεται ως standard C
operator. Ομοίως, δεν συνθέτει \vclmul από generic C loops
(βλ.~\cref{ssec:zvbc-no-autoemit}). Κατά συνέπεια, η μέθοδος
auto-lowering εφαρμόζεται αποκλειστικά σε απλά bit-manipulation patterns
— για κρυπτογραφικούς πυρήνες απαιτούνται ρητά intrinsics.

\paragraph{Σχεδιαστική αρχή.}
Η γενική αρχή που προκύπτει είναι: χρήση της μεθόδου με τον υψηλότερο
βαθμό αφαίρεσης που ικανοποιεί τις απαιτήσεις κάθε πυρήνα. Η assembly
χρησιμοποιείται μόνο όπου δεν υπάρχει εναλλακτική (boot, CSR). Τα
intrinsics χρησιμοποιούνται όπου απαιτείται ρητή πρόσβαση σε
εξειδικευμένες εντολές (\clmul, \vclmul, \vror). Η auto-lowering
αξιοποιείται ως \q{δωρεάν} bonus σε ολόκληρο τον κώδικα μέσω κατάλληλων
\code{-march} flags. Αυτή η ιεραρχία μεγιστοποιεί τόσο την απόδοση
(ρητή χρήση κρυπτογραφικών εντολών) όσο και τη συντηρησιμότητα (ελάχιστος
κώδικας assembly, πλήρης type safety στους πυρήνες).

\paragraph{Σύνδεση με τη βελτιστοποίηση.}
Η αντιστοίχιση κάθε μεθόδου στα συγκεκριμένα αρχεία και πυρήνες της
παρούσας υλοποίησης — μαζί με τεκμηρίωση της σχεδιαστικής απόφασης —
παρουσιάζεται στην~\cref{sec:methods-application}. Τα ποσοτικά
αποτελέσματα ablation (επίπτωση κάθε extension σε isolation) αναλύονται
στην~\cref{sec:isa-ablation}.

\bigskip

Στο παρόν κεφάλαιο παρουσιάστηκε η αρχιτεκτονική πλατφόρμα RISC-V, οι
κρυπτογραφικές επεκτάσεις (scalar και vector) που αξιοποιεί η παρούσα
εργασία, και οι μέθοδοι προγραμματισμού που επιτρέπουν την αποδοτική
αξιοποίησή τους. Το βασικό εύρημα είναι ότι η modular αρχιτεκτονική του
RISC-V — σε συνδυασμό με τυποποιημένες κρυπτογραφικές extensions και
πλούσιο σύνολο C intrinsics — παρέχει τα εργαλεία για υψηλή απόδοση
χωρίς θυσία κρυπτογραφικής ευελιξίας ή φορητότητας. Στο επόμενο κεφάλαιο
εξετάζεται η υπάρχουσα βιβλιογραφία υλοποιήσεων \gls{hqc} σε διάφορες
πλατφόρμες, τεκμηριώνοντας το ερευνητικό κενό που καλύπτει η παρούσα
εργασία.
